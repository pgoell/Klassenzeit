# Kempe BFS bipartiteness fix Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Fix `kempe_build_chain` so it enforces bipartiteness of the chain conflict graph. Without the fix, two chain members can be assigned to the same destination day even when they share a class or teacher, producing a class double-booking that `validate_no_double_booking` catches at production budget on grundschule (item 45, P0).

**Architecture:** Inline same-color cross-check inside `kempe_build_chain` at the new-neighbour insertion site (`solver/solver-core/src/lahc.rs:1314-1320`). Before assigning `chain[neighbour] = neighbour_dest`, walk every existing chain entry whose value equals `neighbour_dest` and reject the chain (`ChainBuild::Aborted`) if any of them shares a class or teacher with the candidate. Pin the bug with one property test (uses the existing widened `lahc_small_problem` generator) and one targeted regression test (pinned to the failing grundschule seed identified via the bench probe).

**Tech Stack:** Rust 1.85, `solver-core` crate (no PyO3, no Python), `proptest` 1.x. Tests live in `solver/solver-core/tests/lahc_property.rs`. Test runner: `cargo nextest run -p solver-core`.

- [ ] **Step 2: Compute neighbour_dest before the new check**

The current code computes `neighbour_dest` *after* the neighbour collection loop, at line 1309:

```rust
        let neighbour_dest = if popped_dest_day == dest_day {
            source_day
        } else {
            dest_day
        };
```

The bipartiteness check must run *during* neighbour collection (we need to know `neighbour_dest` per candidate), so we lift the computation earlier in the loop. Two safe patterns:

a. Compute `neighbour_dest` once at the top of the `while let Some(lesson_id) = frontier.pop_front() { ... }` body, after `popped_dest_day` is resolved.
b. Inline the conditional inside the new check.

Pick (a). After the line:

```rust
        let popped_lesson = match lesson_lookup.get(&lesson_id) {
            Some(l) => *l,
            None => return ChainBuild::Aborted,
        };
        let n = popped_lesson.preferred_block_size;
```

(line ~1241), insert:

```rust
        // Compute the destination day for any new neighbour added under this
        // popped member. The chain alternates source_day / dest_day per BFS
        // depth; new neighbours go to the opposite day from the popped member.
        let neighbour_dest = if popped_dest_day == dest_day {
            source_day
        } else {
            dest_day
        };
```

Then DELETE the equivalent block at lines ~1309-1313 (the old location) so `neighbour_dest` is computed exactly once per popped member.

- [ ] **Step 3: Add the bipartiteness check**

Inside the placements-walking loop, immediately after the `hours_on_source != usize::from(other.preferred_block_size)` block (which currently aborts on block-shape mismatch) and BEFORE the `if !frontier_seen.contains(...)` block, insert:

```rust
                // Bipartiteness invariant: this candidate is about to be
                // assigned `chain[candidate] = neighbour_dest`. Reject the
                // chain if any chain member already at `neighbour_dest`
                // shares a class or teacher with the candidate. Without
                // this check the BFS would silently 2-color a non-bipartite
                // conflict graph, producing same-day same-class collisions
                // at apply time (item 45).
                let same_color_conflict = chain.iter().any(|(existing_id, existing_dest)| {
                    if *existing_dest != neighbour_dest {
                        return false;
                    }
                    let Some(existing_lesson) = lesson_lookup.get(existing_id).copied() else {
                        return false;
                    };
                    let teacher_conflict = existing_lesson.teacher_id == other.teacher_id;
                    let class_conflict = existing_lesson
                        .school_class_ids
                        .iter()
                        .any(|c| other.school_class_ids.contains(c));
                    teacher_conflict || class_conflict
                });
                if same_color_conflict {
                    return ChainBuild::Aborted;
                }
```

The check uses `other` (the candidate lesson resolved from the placements loop, currently bound at line ~1264 via `let other = match lesson_lookup.get(&placement.lesson_id) { Some(l) => *l, None => return ChainBuild::Aborted };`). Confirm `other` is in scope at the insertion point; it is defined inside the same `for placement in placements.iter()` loop body.
