### Testing

- **Session-scoped event loop may cause timing interference at scale.** The `asyncio_default_fixture_loop_scope = "session"` setting (introduced for the Chunk G DB fixtures) means all async tests and fixtures share a single event loop for the entire pytest session. This prevents asyncpg "Future attached to a different loop" errors with session-scoped fixtures but means one slow or stalled async test can delay all subsequent tests in the session. Not a problem with the current 16-test suite, but worth revisiting if the test suite grows large or if tests with long async timeouts are added.
- **Einzuegig solvability test transient flakiness under full-suite ordering.** `backend/tests/seed/test_demo_grundschule_solvability.py` occasionally fails when the full pytest suite runs in xdist worker order but passes when run in isolation. The multi-class lessons PR review noted the symptom is unrelated to the wire-format flip and looks like a pre-existing nondeterminism in `scheduling/teacher_assignment.py:auto_assign_teachers_for_lessons` under full-suite ordering (likely dict-iteration or set-ordering leaking across tests sharing fixture state). Surfaced during the multi-class lessons PR; investigate when the flake reproduces on master CI rather than only locally.

### Production readiness

- **Multi-school tenancy.** The schema today has no `School` table and no `school_id` (or `owner_id`) on any aggregate root. `User` carries only auth fields; route handlers inject `_admin: User` purely for authn / role gating and do not scope queries. Every authenticated user therefore sees and edits the same global pool of teachers, rooms, classes, stundentafel, week schemes, lessons, and placements, so a single deployment can host exactly one school. Multi-tenant work is a coordinated change across (a) a new `schools` table, (b) a `school_id` FK on every aggregate root and on every per-school join row (lessons, placements, availabilities, suitabilities, qualifications), (c) a `school_id` on `User` (or a `school_users` membership table if cross-school admins are real), (d) query scoping in every route handler plus the solver wire-format build (`scheduling/solver_io.py:build_problem_json`), (e) seed scripts and demo fixtures, (f) E2E and integration tests. Revisit before onboarding a second customer school, or before any public / SaaS launch. Until then, single-tenant per deployment is the contract; the staging compose stack is one school, prod will be one school, and a second school means a second deployment.
- **Production DB configuration.** Connection pooling at scale, read replicas, `statement_timeout`, `pg_stat_statements`. All prod concerns, out of scope until the deployment spec.

Move the file into the server-infra tree and update the mount source. Priority: low (only affects cold VPS setups).
