Active sprint program: Solver-driven teacher assignment

Motivation. Today's auto-assign + LAHC pipeline is two greedy heuristics with no shared lookahead: auto_assign_teachers_for_lessons commits a teacher to a lesson based on subject qualification and weekly capacity only, ignoring teacher availability windows and cross-class scheduling pressure. The solver then discovers the resulting allocation is infeasible at solve time (no_free_time_block). 2026-05-08 measurement against test_grundschule_schedule_meets_quality_bar at the production 5000 ms LAHC deadline (item 14): 20/20 RED across 1a, 2a, 3a with the failing class and hour_index drifting run-to-run. A user clicking "Generate Schedule" on a Grundschule today has roughly 100% chance of seeing at least one unplaceable lesson on a fresh seed.

Pivot. Move teacher choice into the solver as a decision variable. User can still pin specific teachers per Lesson (existing UX preserved); otherwise the solver picks among qualified candidates with availability that overlaps the class's available slots. Two new constraints:

  • Hard: for each (class_id, subject_id) pair, all lessons in that pair share the same teacher. New ViolationKind::ClassSubjectTeacherSplit (placement-time check + post-condition validator).
  • Soft: prefer the class's class_teacher_id (Klassenlehrer) for own-class lessons when the Klassenlehrer is qualified. New ConstraintWeights.prefer_class_teacher weight; the LAHC slice and CP-SAT objective both penalise unmet pairs.

Outcome target. test_grundschule_schedule_meets_quality_bar and test_seeded_grundschule_solves_without_pinned_teachers go deterministically green; the user-experience for "click Generate" becomes one-shot reliable on every Grundschule fixture. Sprint 4's differenziert (E-Kurs / G-Kurs) remains out of scope; the per-(class, subject) uniformity constraint is correct for Grundschule + Sek I einzügig and gets extended (likely via a differentiation_group_id) when Sprint 4's fixtures land.

Phase ordering: ADR first (load-bearing decision); then schema, wire-format, algorithm, backend, frontend, tidy. ADR 0036 (this sprint's foundational ADR) landed via item 61; item 47's planned production-default ADR claims at minimum 0037 (always ls docs/adr/*.md | sort | tail -1 before assigning; ADR 0035 is the Timefold-rejection from item 55).

Production readiness

  • Multi-school tenancy. The schema today has no School table and no school_id (or owner_id) on any aggregate root. User carries only auth fields; route handlers inject _admin: User purely for authn / role gating and do not scope queries. Every authenticated user therefore sees and edits the same global pool of teachers, rooms, classes, stundentafel, week schemes, lessons, and placements, so a single deployment can host exactly one school. Multi-tenant work is a coordinated change across (a) a new schools table, (b) a school_id FK on every aggregate root and on every per-school join row (lessons, placements, availabilities, suitabilities, qualifications), (c) a school_id on User (or a school_users membership table if cross-school admins are real), (d) query scoping in every route handler plus the solver wire-format build (scheduling/solver_io.py:build_problem_json), (e) seed scripts and demo fixtures, (f) E2E and integration tests. Revisit before onboarding a second customer school, or before any public / SaaS launch. Until then, single-tenant per deployment is the contract; the staging compose stack is one school, prod will be one school, and a second school means a second deployment.
