# Klassenzeit backend: rules

Stack: FastAPI + SQLAlchemy async, Alembic, Pydantic. Served under `klassenzeit_backend`. Rules below are on top of `.claude/CLAUDE.md`, not a replacement.

## Layout (`backend/src/`)

- Routes and route handlers live next to the aggregate they serve.
- Runtime state (engine, session factory, settings, rate limiter) lives on `app.state`, set in `lifespan`. No module-level globals.

## Runtime state

- **`app.state` for FastAPI runtime state.** Engine, session factory, settings, and rate limiter live on `app.state` (set in `lifespan`). Tests set these on `app.state` in the `client` fixture. No module-level globals.

## Error handling

- **No bare catchalls.** No bare `except:` / `except Exception` in Python. Catch the specific error you can handle; let the rest propagate.
- **Use `status.HTTP_422_UNPROCESSABLE_CONTENT`** for 422 responses. The older `HTTP_422_UNPROCESSABLE_ENTITY` alias is deprecated in the Starlette/FastAPI stack we pin and raises a `DeprecationWarning` at import.

## Type checking

- **`ty` does not honor `# type: ignore[...]` pragmas.** If `ty` flags a line, silencing it requires the actual type, not a comment. Prefer concrete types (NamedTuple, TypedDict, a tiny dataclass) over returning `dict[str, object]` from helpers that `ty` will traverse.
- **Pre-commit `ty check` blocks a strict "red test with missing module" TDD start.** A test that imports a not-yet-created module fails `ty`'s `unresolved-import` gate, and `ty` has no per-file carve-outs or pragmas. Land a stub module (typed `AsyncSession` signature, body `raise NotImplementedError(...)`) in the red commit; tests still fail at runtime, which is a valid red. Replace the body in the next commit.
- **Don't add `from __future__ import annotations` to test files or backend Pydantic schema modules.** Ruff `TC001/TC002/TC003` then flags every annotation-only import (e.g. `import uuid`, `from collections.abc import Sequence`) as "needs to move into a `TYPE_CHECKING` block." The repo's sibling test/schema files don't use the future import; match them.

## Data access

- **No raw SQL outside the abstraction layer.** All queries go through SQLAlchemy (or whatever repository layer lands later). If raw SQL is unavoidable, it lives inside the data-access module, never in route handlers or business logic.
- **Alembic autogenerate style drift.** `alembic revision --autogenerate` emits `typing.Sequence` and `typing.Union[X, Y]` imports. Repo style is `collections.abc.Sequence` + PEP 604 unions (`X | Y`). Tidy the new revision file before committing; `ruff` does not flag it.
- **Native Postgres `ENUM` columns with a Python `enum.StrEnum` need `values_callable`.** SQLAlchemy 2 sends `member.name` (`GYMNASIUM`) on the wire by default, but the Postgres `CREATE TYPE` carries `member.value` (`Gymnasium`); the round-trip then errors with `psycopg.errors.InvalidTextRepresentation: invalid input value for enum`. Pin the column declaration to `PG_ENUM(SchoolType, name="school_type", create_type=False, native_enum=True, values_callable=lambda enum_cls: [m.value for m in enum_cls])` plus `server_default=SchoolType.<DEFAULT>.value`. The Alembic migration creates the type explicitly with `school_type_enum.create(op.get_bind(), checkfirst=True)` (and `drop(...)` on downgrade); idempotent under the test-template DB cache. Pattern in `db/models/stundentafel.py:Stundentafel.school_type` and `alembic/versions/d89dceb4a06e_add_stundentafel_school_type.py`.
- **`ALTER COLUMN ... TYPE` needs `DROP DEFAULT` first when the existing default has incompatible type.** Postgres rejects the cast otherwise. Canonical shape: `ALTER COLUMN <c> DROP DEFAULT, ALTER COLUMN <c> TYPE <new> USING (<expr>), ALTER COLUMN <c> SET DEFAULT <new-default>, ALTER COLUMN <c> SET NOT NULL` in one `op.execute(...)` per column. The `BOOLEAN → INTEGER` flip in `09dab109a11c_subject_preference_weights.py` is the template; reverse the order for the lossy downgrade.
- **`AsyncSession.execute(delete/update).rowcount`.** `ty` sees the return as `Result[Any]`; `.rowcount` only exists on runtime `CursorResult`. Access it via `int(getattr(result, "rowcount", 0) or 0)`. Pattern in `auth/sessions.py:66-76`.
- **PATCH handlers for nullable columns must use `body.model_fields_set`, not `is not None`.** The default pattern `if body.foo is not None: orm.foo = body.foo` silently drops explicit `null` updates. For nullable FKs and similar fields where clearing is a real intent, gate on `if "foo" in body.model_fields_set: orm.foo = body.foo` so an explicit null clears the column. Keep the `is not None` shape for NOT NULL columns where null has no meaning. Pattern in `scheduling/routes/school_classes.py:update_school_class_route` (`home_room_id` clear path; `max_lessons_per_day` follows the same pattern, ADR 0033).
- **Routes that mutate DB state must explicitly `await db.commit()` + `await db.refresh(orm_row)` before returning.** The test conftest overrides `get_session` with a savepoint-wrapped shared session, so a missing commit silently passes route tests; production fails because each request gets a fresh `session_factory()` with no caller-side commit, so writes roll back at end-of-request. Sprint C found this latent bug in `POST /api/classes/{id}/schedule`, `POST /api/schedule/all`, and the new `placements.py` endpoints (fix landed in commit `7542d6f`). Templates: `lessons.py` and `rooms.py` (correct from day one).

## Testing

- **Test fixtures, not imports.** `pytest` runs with `--import-mode=importlib`. Shared test helpers must be pytest fixtures (factory pattern) in `conftest.py`, not plain functions imported across test files. Cross-conftest imports break silently.
- **Scheduling entity-aggregate factories** live in `backend/tests/scheduling/conftest.py`: `create_subject`, `create_week_scheme`, `create_time_block`, `create_room`, `create_teacher`, `create_stundentafel`, `create_stundentafel_entry`, `create_school_class`. Join-table rows (`Lesson`, `TeacherQualification`, `TeacherAvailability`, `RoomAvailability`, `RoomSubjectSuitability`) have no factory; construct inline with `db_session.add(...)` + `await db_session.flush()`. `Lesson.preferred_block_size` is NOT NULL with no server default; always set it (typically `1`).
- **`TimeBlock.start_time` / `end_time` are `datetime.time`,** not strings. Pass `time(8, 0)`, not `"08:00"`.
- **`Teacher` ORM has no `qualifications` relationship attribute; query `TeacherQualification` directly.** `db/models/teacher.py` defines `Teacher` and `TeacherQualification` as separate classes with no `relationship(...)` between them; `selectinload(Teacher.qualifications)` is invalid. Use the pattern from `_build_teacher_detail` in `scheduling/routes/teachers.py`: `select(Subject).join(TeacherQualification, TeacherQualification.subject_id == Subject.id).where(TeacherQualification.teacher_id == teacher.id)`. For list endpoints that need qualifications for many teachers, run one bulk query `select(TeacherQualification.teacher_id, TeacherQualification.subject_id).where(TeacherQualification.teacher_id.in_(teacher_ids))` and group in Python; this is the shape used by `list_teachers` after item 70's `subject_ids` addition. Same shape applies to `TeacherAvailability` (also a separate model, no `Teacher.availability` attribute).
- **`async with db_session.begin_nested():` for tests that expect `IntegrityError`.** The `db_session` fixture wraps every test in an outer nested savepoint; a bare `await db_session.rollback()` in `finally:` escapes the inner savepoint and drops pre-inserted setup rows. Use the `async with` form so the rollback stays scoped. Pattern in `tests/seed/test_demo_grundschule_rollback.py`.
- **`Lesson.teacher_id` is a pin-only hint; the solver picks among `teacher_candidates` when it is null.** `scheduling/solver_io.py:build_problem_json` does NOT filter by teacher anymore (item 63 removed the `IS NOT NULL` clause), and `POST /api/classes/{id}/generate-lessons` no longer pre-assigns a teacher (the auto-assign call was removed in the same item). Newly-generated Lessons reach the solver with `teacher_id: null` and a non-empty `teacher_candidates` list, and the solver picks one per ADR 0036. Seed tests that want a specific allocation (e.g. to keep the bench fixture's pinned cell shape stable across refreshes) still pin `teacher_id` inline via SQL UPDATE; tests that want to exercise the solver's picker leave it null. Pattern in `tests/seed/test_demo_grundschule_solvability.py`. **Per item 69, `POST /api/classes/{id}/generate-lessons` validates qualified-teacher coverage up front: if any curriculum subject has zero qualified teachers, the route returns 422 with a structured detail dict (`code="missing_qualified_teacher"`, plus `subject_ids` and `subject_short_names`) before generating any Lessons.** The validation runs against `TeacherQualification` rows for every Stundentafel subject in the class's curriculum; a class whose Stundentafel references a subject no teacher is qualified for cannot generate lessons until the gap is closed via teacher edits or a Stundentafel edit.
- **Solver post-condition validators raise `ValueError`, not soft violations.** `solver_io.run_solve` catches `(ValueError, RuntimeError)` from the Rust side, logs `solver.solve.error` with `exc_class`, and re-raises. The Rust validator quintet (`validate_no_double_booking`, `validate_no_room_hopping`, `validate_daily_caps`, `validate_placement_teacher_in_candidates`, `validate_class_subject_teacher_uniformity`; full list and wiring in `solver/CLAUDE.md` under "Post-condition validators quintet") `bail!` on a violation rather than emitting a `ViolationKind`, so a buggy solver output surfaces as `ValueError("input: double-booking")` (or similar) propagating out of `POST /api/classes/{id}/schedule` as an HTTP 500 (or as a raised exception under `httpx.ASGITransport(raise_app_exceptions=True)`). Tests must check `sched_resp.status_code == 200` BEFORE asserting on `body["violations"]`; a soft-violation assertion alone misses the validator path. Surfaced by item 32: the seed solvability sibling tests (renamed under item 11 to `test_seeded_grundschule[_zweizuegig|_dreizuegig]?_solves_without_pinned_teachers`) catch this case as a fail mode and reflect it as XFAIL via the `pytest.mark.xfail(strict=False, reason=...)` pattern. **A second backend-test panic shape comes from the maturin dev wheel.** `mise run solver:rebuild` produces a debug-profile wheel by default, so the LAHC per-iteration `debug_assert_eq!(state.canonical_score, score_solution(...))` (item 52's drift detector) fires inside `klassenzeit_solver` during `mise run test:py`, surfacing as `pyo3_runtime.PanicException` propagating out of `solver_io.run_solve`. When a backend test panics with that exact message, the fix lives in `solver-core/src/lahc.rs`, not in the backend; see the matching pointer in `solver/CLAUDE.md`'s "Maturin dev loop" section.
- **Capture the failing backend Problem JSON by tee-ing `problem_json` from `run_solve` into `/tmp/`.** When a backend integration test surfaces a solver bug that can't be reproduced against `solver-core::test_fixtures::*_fixture()` (per the bundled-fixtures rule in `solver/CLAUDE.md`), the fastest diagnostic is a temporary instrumentation in `scheduling/solver_io.run_solve` that writes `problem_json` to a per-call file under `/tmp/` BEFORE the `solver_backend match`: `pathlib.Path("/tmp") / f"item-N-problem-{uuid.uuid4().hex[:8]}.json"`. Run the test once, identify the failing call's dumped JSON (in a per-class `/schedule` flow, the LAST `ITEM_N_PROBLEM_DUMPED` line before `solver.solve.error` is the failing problem), then build a Rust regression test that loads the JSON via `include_str!` or rebuilds the failing scenario inline. Revert the instrumentation before committing. The pattern works because `solve_json_with_config` is the same code path the bench uses, so a JSON-replay test in Rust reproduces deterministically. Surfaced 2026-05-11 diagnosing item 77 (the bug fired on per-class-sequential `/schedule` calls where prior classes' placements arrived as `pinned_placements`; the bundled `grundschule_fixture` has zero pins so the in-tree path doesn't reach the buggy seed sites). Same shape applies to any future backend-only solver bug whose reproducer requires the production wire format's exact shape.
- **Greedy-assignment heuristics: sort the input by a stable constraint metric.** The historical canonical example is `auto_assign_teachers_for_lessons` (formerly in `scheduling/teacher_assignment.py`, deleted under OPEN_THINGS item 69 alongside the Lesson.teacher_id pin-only flip in item 63 and the solver-driven teacher pick in items 64-68): it sorted lessons in ascending order of qualified-teacher count (subjects with one qualified teacher first) before walking each lesson's candidate teachers. Pure first-fit on the StundentafelEntry iteration order is non-deterministic across runs because subject UUIDs are random; if a placeholder heuristic in this codebase grows, follow the scarcity-first pattern rather than relying on insertion order.
- **Seed solvability tests drive the HTTP route flow.** There is no public `generate_lessons_for_class` helper; lesson generation lives only inside the `POST /api/classes/{id}/generate-lessons` route handler (auto-commits on its own session). Solvability tests for `demo_*` seeds (`test_demo_*_solvability.py`) seed entities, then call the HTTP endpoint, then `POST /api/classes/{id}/schedule`, then assert on the response. The HTTP route is the only production code path that materialises Lessons from a Stundentafel; calling a private helper directly would diverge from production.
- **Seed modules import sibling seed modules' `_`-prefixed shared constants.** `demo_grundschule_zweizuegig.py` imports `_PERIODS`, `_SUBJECTS`, `_GRADE_*_HOURS`, `_KLASSENRAUM_SUITABLE_SUBJECTS`, and the NamedTuple types from `demo_grundschule.py` rather than copying them. Cross-module access of `_`-prefixed names is intentional here: the seed package treats these as package-internal shared data; copying would create the cross-fixture drift this PR was designed to prevent.
- **Sibling seeds' `Subject(...)` constructors drift silently from the einzügig kwarg list.** `demo_grundschule_zweizuegig.py` and `demo_grundschule_dreizuegig.py` each iterate `_SUBJECTS` but materialise rows via their own local `Subject(...)` constructor; if a kwarg present on `_SubjectSpec` is missing from one of those constructors, the field's value drops to its schema default (typically 0) without any error or warning. Item 12 surfaced this: `_SUBJECTS` already had `prefer_late_period` available, but `prefer_late_period=spec.prefer_late_period` was only present in `demo_grundschule.py`, so the zweizuegig and dreizuegig seeds silently dropped the value. When `_SubjectSpec` (or the `_TeacherSpec` / `_RoomSpec` parallel cases) gains a new field, audit each sibling seed's matching `Subject(...)` / `Teacher(...)` / `Room(...)` constructor in lockstep.
- **`_TEACHER_ASSIGNMENTS_<NAME>` dicts pin teacher allocation in seed solvability tests.** A `dict[tuple[str, str], str]` mapping `(class_name, subject_short) → teacher_short_code`, owned by the seed module but not consumed by its coroutine; since item 63 flipped `Lesson.teacher_id` to pin-only semantics, `POST /generate-lessons` leaves `teacher_id` null and the solvability test's SQL `UPDATE` after `generate-lessons` is now the SOLE source of pinned teachers (no auto-assign to override). The pinning keeps the matching Rust bench fixture's cell shape stable across refreshes by collapsing the per-Lesson teacher decision to a singleton. **Implication for cross-referencing bench data:** integration tests that intentionally exercise the solver-driven assignment path (e.g. `test_grundschule_schedule_meets_quality_bar`, which calls the HTTP route and does NOT run the override `UPDATE`) see a different and harder problem cell than the bench fixture, because the solver picks among `teacher_candidates` per Lesson rather than seeing a pre-pinned teacher. Bench `Quality (pass / 4)` and per-component median columns describe the pinned cell; they do not predict pass on the solver-driven-assignment integration test. See the matching pointer in `solver/CLAUDE.md` under "Bench `Quality (pass / 4)` data does NOT predict integration-test pass on the solver-driven teacher path".
- **`caplog` records expose `extra=` keys via `record.__dict__[key]`, not `record.key`.** `ty` rejects `record.foo` with `unresolved-attribute` because `LogRecord` has no static schema for `extra=`-injected fields, and `ruff` B009 rejects `getattr(record, "foo")` for static string keys. The working pattern is `record.__dict__["foo"]`. Pattern in `tests/scheduling/test_solver_io.py:test_run_solve_round_trips_and_logs`.
- **Settings tests construct `Settings` directly, not `get_settings()`.** Use `Settings(_env_file=None)  # ty: ignore[missing-argument, unknown-argument]` after the `monkeypatch.setenv("KZ_*", ...)` calls. Avoids the `lru_cache.cache_clear()` dance the obvious template suggests. Pattern in `tests/core/test_settings.py`.
- **Ruff `PLC0415` rejects in-function imports.** Hoist all imports to module top-level even when a test only needs them once. Affects the `monkeypatch.setattr(some_module, ...)` pattern where the obvious move is to import the module inline; import at the top instead.
- **Middleware integration tests use `httpx.ASGITransport(app=build_app(env="dev"))`** + `AsyncClient` + `caplog.set_level(logging.INFO, logger="...")`. Pattern in `tests/test_http_access_middleware.py`. Inline route registration on a built app works: `app = build_app(...); @app.get("/__probe")\nasync def _probe(): ...` is accepted because routes go on `app.router` (not the middleware stack), so a one-off probe endpoint can live inside the test body without mounting the testing router. Used by `test_request_id_propagates_to_route_handler_log` to assert filter-driven enrichment without leaking a "log a line" call site into `/api/health`.
- **Cross-test-module helpers import as `from tests.<module> import ...`,** NOT `from backend.tests.<module> import ...`. There is no `backend/__init__.py`; with `--import-mode=importlib`, the package root is `tests/` (the first ancestor with `__init__.py`). New helper modules under `backend/tests/` (e.g., `_xdist_db.py`) are imported via `from tests._xdist_db import ...` from sibling test files and from `conftest.py`. Note this is for non-fixture helpers (pure functions); fixtures still belong in a `conftest.py` per the rule above.
- **Conftest module-load env mutations need `# noqa: E402` on trailing `klassenzeit_backend` imports.** Ruff E402 tolerates a single trivial statement between imports (the existing `os.environ.setdefault("KZ_ENV", "test")`) but trips on multi-line conditional logic (the per-worker DB suffix block). The `klassenzeit_backend.*` imports must come AFTER the env mutation so `lru_cached get_settings()` lands the right URL; mark each with `# noqa: E402`. Pattern in `backend/tests/conftest.py`.
- **pytest-xdist runs each worker against its own database.** `backend/tests/_xdist_db.py` exposes pure helpers: `worker_database_url`, `ensure_database_exists`. The conftest reads `PYTEST_XDIST_WORKER` (set to `gw0`/`gw1`/... per worker, `master` or unset otherwise), suffixes `KZ_DATABASE_URL` accordingly, and `apply_migrations` calls `ensure_database_exists` to idempotently create the per-worker DB before running alembic. Sequential `mise run test:py` uses `klassenzeit_test` unchanged. ADR 0019.
- **Alembic migrations are cached via a Postgres template database.** `_xdist_db.py` exposes `ensure_template_database`, `clone_database_from_template`, `drop_database_if_exists`. `apply_migrations` opportunistically uses `klassenzeit_test_template` under a `pg_advisory_lock` so only the first worker actually runs alembic; subsequent workers `CREATE DATABASE ... TEMPLATE`. Falls back to per-worker `alembic downgrade base + upgrade head` if the template path raises (locale mismatch, permission, etc.); the fallback logs `template_db.fallback` at WARNING. (ADR 0019 originally rejected this in favour of per-worker migrations and was later superseded by the implementation here; no separate ADR was opened.)
- **Schema-changing PRs: drop the template + per-worker DBs before the first test run.** The conftest's template cache means `klassenzeit_test_template` and any pre-existing `klassenzeit_test_gwN` worker DBs were cloned from the *previous* schema. Running `mise run test:py` against the new branch surfaces as `psycopg.errors.UndefinedTable: relation "<new_table>" does not exist` per worker. Recovery: connect to postgres and `DROP DATABASE IF EXISTS klassenzeit_test_template; DROP DATABASE IF EXISTS klassenzeit_test_gw0; ...` (or just drop everything matching `klassenzeit_test%`). **Drop `klassenzeit_test` (no suffix) too** in the same step: it's the sequential-mode DB used when `PYTEST_XDIST_WORKER` is unset, and the conftest only re-migrates the template + per-worker DBs on first run. The conftest then re-migrates the template idempotently on the next run. `mise run db:reset` only resets the dev DB, not the template/worker family.
- **`KZ_SOLVE_DEADLINE_MS=0` in `backend/.env.test` makes backend tests greedy-only.** Settings field `solve_deadline_ms: int | None = 5000` (raised from 200 ms in ADR 0033 so hard problems get LAHC headroom while easy ones still complete in <100 ms via the canonical-floor early-exit); the route handler reads it from `app.state.settings.solve_deadline_ms` and threads it into `solver_io.run_solve(..., deadline_ms=...)`. Tests opt out of the LAHC wall-clock by default; production keeps the 5000 ms LAHC pass. **One-test override:** `monkeypatch.setattr(app.state.settings, "solve_deadline_ms", 5000)` opts a single test back into LAHC at the production budget (ADR 0033). Use sparingly: only when the test is asserting a soft-cost-driven property (gap, balance, home-room ratio) that LAHC delivers but greedy alone cannot. Pattern in `backend/tests/scheduling/test_grundschule_schedule_quality.py`.
- **`KZ_SOLVER_BACKEND` selects the solver backend.** `Settings.solver_backend: Literal["lahc", "lahc_rr", "lahc_rr_kempe", "cpsat"]`, default `lahc_rr_kempe` per [ADR 0031](../docs/adr/0031-solver-production-default.md), reaffirmed against the post-item-37 corrected bench data in [ADR 0032](../docs/adr/0032-solver-production-default-revisit.md). The route handlers in `scheduling/routes/schedule.py` read `request.app.state.settings.solver_backend` and pass it as a kwarg to `solver_io.run_solve`, which dispatches on it via a `match` statement. The `cpsat` backend depends on the `ortools` Python wheel (~50 MB); the three LAHC variants are pure-Rust with different period kwargs to `solve_json_with_config`. The default is pinned by `tests/core/test_settings.py::test_solver_backend_default_is_production_choice`; flip the assertion and the ADR in lockstep when a future bake-off refresh changes the verdict. ADR 0030 documents the cpsat dependency direction; ADR 0031 + ADR 0032 document the production-default decision.
- **Tests asserting a quality bar the production system does not yet meet ship as `pytest.mark.xfail(strict=False)`.** Keeps the regression guard alive (a future improvement turns the test green and the xfail comes off in lockstep) without blocking CI today. Pair every xfail with a sibling item in `docs/OPEN_THINGS.md` "Acknowledged deferrals" naming the unblocking work. Pattern in `test_grundschule_schedule_quality.py`.
- **Adding a column to a table whose route handlers manually construct response objects requires updating each manual construction site.** Subject's POST/PATCH/GET in `scheduling/routes/subjects.py` build a fresh `SubjectResponse(...)` per call rather than using `model_validate(orm_row)`, so a new column won't auto-flow. The `read_schedule_for_class` / `read_schedule_for_teacher` / `read_schedule_for_room` helpers in `scheduling/solver_io.py` follow the same shape: each builds `PlacementResponse(...)` with explicit kwargs, so a new field on `PlacementResponse` requires threading `<field>=row.<field>` through all three sites or the persisted-read GET endpoints raise Pydantic `ValidationError` at request time. Audit each `model_construct` / direct-instantiation site after `alembic revision`, AND after any additive Pydantic schema field added to a model that the manual-construction sites populate. Templates that DO auto-flow: anything using `SubjectResponse.model_validate(orm)` or `.model_dump()` over a query result. Pattern surfaced when adding `Subject.prefer_late_period`; reaffirmed 2026-05-10 closing OPEN_THINGS item 69 when adding `PlacementResponse.teacher_id`.
- **Structured 422 detail dicts: `{"code": str, ...domain fields}` is the project convention for machine-readable error codes.** FastAPI accepts `HTTPException(status_code=..., detail=<dict>)` natively; a dict carries a stable `code` discriminator the frontend can switch on for i18n, plus domain fields the user can act on (e.g. `subject_ids`, `subject_short_names`). Plain string `detail` remains fine for one-shot human-readable errors that have no frontend handler. Existing example: `_validate_qualified_teacher_coverage` in `scheduling/routes/lessons.py` (OPEN_THINGS item 69). Pattern: aggregate every offender into one response when the user's natural fix-batch is "fix all gaps at once" rather than "fix one, retry, fix another." When adopting this in a new error site, lift only when the frontend or admin has a real action keyed off the `code`; do not retrofit existing string-detail 422s without a downstream consumer.
- **`Subject.short_name` and `Teacher.short_code` are different column names for the same conceptual "short identifier" field.** When error details, log fields, and serialization helpers expose either, keep the names aligned with the source model (`subject_short_names`, `teacher_short_codes`); a field named `subject_short_codes` is wrong because Subject has no `short_code` column. Surfaced 2026-05-10 during the item 69 plan review when the spec used `subject_short_codes` and the reviewer flagged the drift against the actual ORM column.
- **Adding a NOT NULL column to `scheduled_lessons` cascades to test bodies plus `placements.py` move/swap mutators.** `ScheduledLesson(...)` is constructed inline in ~12 sites across `tests/scheduling/{conftest,test_solver_io,test_schedule_persistence,test_scheduled_lesson_pinned_column}.py` (no shared factory exists for this table); pytest's `IntegrityError`s after the alembic upgrade enumerate offenders. Beyond tests, `scheduling/routes/placements.py`'s move and swap mutators rebuild `ScheduledLesson` rows from prior rows; non-key fields (now including `teacher_id` after item 65; soon any future column) must be threaded through from the source row, since move/swap changes the (time_block, room) slot but does not change which teacher teaches the lesson. Fixture helpers in `conftest.py` like `seeded_lesson_for_pinning` may need to expose the new field on their return shape (typically as an extra tuple element) so test bodies can read it without re-querying. Surfaced 2026-05-08 adding `ScheduledLesson.teacher_id` for OPEN_THINGS item 65.
- **Pin-collector helpers in `solver_io.py` thread every wire-format-significant `ScheduledLesson` field.** `collect_pinned_placements` (cross-class drift guard on per-class `/schedule`), `collect_own_class_pins` (focus-class pinned slots), and `collect_all_pins` (whole-school `/schedule`) each build `{"lesson_id", "time_block_id", "room_id", "teacher_id", ...}` dicts from `ScheduledLesson` rows for the solver wire format (`PinnedPlacement` per solver/CLAUDE.md item 77). When a new `ScheduledLesson` column becomes part of the solver pin contract (today: `teacher_id`; future: any per-placement decision the picker should consume), every one of these three helpers must read `row.<field>` and include it in the dict, otherwise the seed Placement falls back to a wrong default and the pre-solve readers in `solver-core/src/solve.rs` (`validate_pins`, `seed_greedy_state_from_pins`) silently corrupt state. Distinct from the `placements.py` move/swap rule above (which guards row-rebuild on user-driven mutations); this rule guards the read path that flows persisted state into the solver as pins. Surfaced 2026-05-11 closing item 77: `ScheduledLesson.teacher_id` had been on the schema since item 65 but the three collectors built dicts without it, so the solver's seed used `assigned_teacher_id()`'s `teacher_candidates[0]` fallback and `validate_no_double_booking` rejected the output on per-class-sequential `/schedule` under unpinned mode.
- **`build_problem_json` SQL loads must broaden in lockstep when a wire-format key shifts from a singular FK to a candidate list.** When `Lesson` ships a single FK on the wire (`teacher_id: T`) and the SQL pre-selects only the pinned teacher's `Teacher` / `TeacherQualification` / `TeacherAvailability` rows, broadening the wire format to `teacher_candidates: [T1, T2, ...]` requires broadening every contributing load: filter `TeacherQualification` by the lessons' subjects (not the pinned-teacher subset), load all qualified teachers (not just pinned), load every qualified teacher's availability against the relevant time-block set. Without this, the candidate-set computation degenerates to `[teacher_pin]` and looks correct on a single-teacher fixture but misses every other qualified teacher in production. Catch at plan time by enumerating "what does the new wire-format key need to know about?" and broadening the source SQL alongside. Surfaced 2026-05-08 implementing item 64. Same shape applies to any future wire-format pluralisation (e.g. multi-room lessons, role candidates).
- **`build_problem_json` candidate-availability filter: zero `TeacherAvailability` rows means universally available.** Existing convention used by `teacher_blocked_times` (the wire format only emits an entry when `a.status != "available"`); a teacher with no availability rows at all is treated as available everywhere. The candidate-set computation in `_candidates_for_lesson` follows the same shape: a teacher with no availability rows is a valid candidate for every time block. A strict "must overlap" rule breaks every pre-existing test that seeds a Teacher without availability rows (e.g. `test_run_solve_honors_subject_daily_hour_cap`). Pattern surfaced 2026-05-08 implementing item 64; documented in `_candidates_for_lesson`'s docstring.
- **`build_problem_json` returns `tuple[str, set[UUID], dict[str, int]]`,** not a single string. Direct unit tests unpack as `problem_json, class_lesson_ids, input_counts = await build_problem_json(...)`. The `class_lesson_ids` set is empty when called with `class_id=None` (whole-school path); `input_counts` carries per-table row counts for observability. Pattern in `backend/tests/scheduling/test_solver_io.py`. Surfaced 2026-05-09 closing OPEN_THINGS item 63 when adding a direct unit test of the function.
- **`DELETE /api/teachers/{id}` and `DELETE /api/users/{id}` are soft deletes.** Both `Teacher` and `User` have an `is_active: bool` column; the route handlers set `is_active=False` and return 204 (`scheduling/routes/teachers.py` and `auth/routes/admin.py`). The DB row stays, so FK `ON DELETE SET NULL` / `ON DELETE CASCADE` does NOT fire. Tests that need to exercise an FK cascade against `Teacher` (or `User`) must hard-delete via the session: `await db_session.delete(teacher); await db_session.flush(); db_session.expire_all()`. Other CRUD entities (Room, Subject, SchoolClass, Stundentafel, WeekScheme, Lesson) use hard delete via `await db.delete(orm); await db.commit()`. Surfaced 2026-05-08 closing OPEN_THINGS item 62, where the schema-cascade test for `class_teacher_id` initially used the HTTP DELETE route and observed no cascade because the Teacher row was never deleted.
- **`ViolationResponse.kind` Literal lives in `scheduling/schemas/schedule.py`,** not `api/schemas.py`. Adding a new `ViolationKind` variant to the solver Rust enum cascades: (a) widen the Pydantic `Literal[...]` union here, (b) `mise run fe:types` to regenerate `frontend/src/lib/api-types.ts`, (c) extend the exhaustive switch in `frontend/src/i18n/violation-keys.ts` (TypeScript flags a missing case as a real `tsc --noEmit` error after step b, so the switch will not type-check until you add a case + an i18n key in `frontend/src/i18n/locales/{de,en}.json`), (d) update the two closed-enum tests in `backend/tests/scheduling/test_solver_io.py` (`test_count_violations_by_kind_clean_solve_returns_zeros` and `test_count_violations_by_kind_aggregates_mixed_kinds`). Land all four in the same commit.

## Logging

- **Structured-log events use `logger.info("event.name", extra={...})`.** `core/logging.py:JsonFormatter` merges `extra=` keys into the JSON record at top level via the `_RESERVED` denylist. Reserve `event` as a stable identifier (e.g. `solver.solve.done`, `http.request`); never f-string-interpolate the message. Configured once per process from `build_app` via `configure_logging(env, log_format, log_level)`. JSON is the default in `KZ_ENV=prod`; dev/test stay plain text. ADR 0016.
- **Per-request access log lives on `klassenzeit_backend.http.access`.** The `@app.middleware("http")` handler in `main.py` emits `event=http.request` with `method`, `path`, `status`, `duration_ms`, `request_id`. Inbound `X-Request-ID` is preserved and echoed; absent or oversized (>64 chars) headers regenerate via `_resolve_request_id` from `core/logging.py`.
- **Per-request `request_id` propagates automatically via `request_id_var`** (a `ContextVar[str | None]` in `core/logging.py`). The access middleware sets it after `_resolve_request_id` and resets it in a `finally`. A `RequestIdFilter` on the root stream handler injects the value onto any `LogRecord` emitted inside the request scope that does not already carry `request_id`. Routes do not need to thread `request_id` through `extra=`; explicit `extra={"request_id": "..."}` still wins (e.g. for a background task tagging a follow-up event with the originating request's id). Records emitted outside a request scope (startup, lifespan, non-request asyncio tasks) leave `request_id` absent.
