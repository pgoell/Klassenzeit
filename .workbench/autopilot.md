## Project-specific rules

**Solver-binding rebuild discipline.** When a subagent runs Python or backend integration tests that consume `klassenzeit_solver` (the maturin-built PyO3 binding) AFTER an earlier task in the same autopilot run touched `solver/solver-core/` or `solver/solver-py/`, the agent's prompt MUST include `mise run solver:rebuild` as an explicit step before pytest. Otherwise the binding is stale and the agent observes phantom wire-format bugs (a Sprint A subagent misdiagnosed a non-existent `kind`-as-tagged-dict bug from a stale binding). Same shape applies to `mise run fe:types` after backend Pydantic schema changes if the next task touches frontend types.

**OPEN_THINGS.md hygiene at step 6.** `docs/OPEN_THINGS.md` is for OPEN items only. Specifically:

- When an item ships, DELETE it from OPEN_THINGS entirely. Do not leave a `✅ Shipped <date> in PR #<N>` line behind. The PR description and `git log` are the canonical record of what shipped; OPEN_THINGS is the canonical record of what is still open.
- When a PR closes the last open work in the active sprint program, promote the next `## Queued sprint: ...` to `## Active sprint program: ...` and DELETE the closed sprint section. Open quality / tuning items the closed sprint deferred move to a `## Open <topic> follow-ups` section between the new active sprint and `## Planned future sprints`, NOT to a "Completed" section (no such section exists in this file).
- When an item under `## Acknowledged deferrals` closes (intentionally or by side effect), DELETE the entry. Do not leave "Closed YYYY-MM-DD" annotations.
- When the item that ships was promoted from a `## Open <topic> follow-ups` stub (the stub's body says `[Promoted to P0, see active-sprint item N]` or similar), DELETE the stub too. The promoted-and-shipped chain leaves no trace.
- PR-number references that name PRs from the lifetime of an open item (e.g., "the regression PR #171 left this xfail behind") are fine: those name a still-relevant historical anchor for an open item. The rule is about closed items, not historical references.
- `## Reference data` (e.g., the Hessen Grundschule reference table) is research that future sprints consume and stays in the file.
- When closing an item that takes a previously-unassigned ADR number, `grep -n "ADR <NNNN>" docs/OPEN_THINGS.md` and refresh every stale reference in the same commit. Items can pre-claim an ADR number in their bodies (e.g., item 47 said "open ADR 0035 (next-available number)" before item 55 actually claimed 0035), and stale references can sit in unrelated items' bodies, in section preambles, and in the active-sprint header. The plan's edit list often only enumerates references inside the closing item itself, missing the others.
- Same shape applies to OPEN_THINGS item numbers: when closing item N, `grep -n "item N" docs/OPEN_THINGS.md` and refresh forward-looking references in OTHER active items' bodies (lines that say "consumes item N's refresh", "blocked by item N", "informed by item N's data"). Past-tense narrative references inside another item's `**shipped**` ship-event paragraph are historical anchors and stay. Closing item 44 on 2026-05-08 required updating item 47's "consumes item 44's full refresh" wording in the same commit; item 22's "the directional read defers to item 44's full refresh" inside its ship narrative was historical and was not touched. The plan's edit list often enumerates only the closing item's own bullet, missing forward-looking references in adjacent items.
- When closing the last item under an `### <Phase> phase` header inside the active sprint program, DELETE the empty header alongside the bullet. Empty section scaffolding is doc noise, and an OPEN_THINGS reader scanning for the next pickup should not have to skip past content-free headers. Same shape applies to any `### Tier` / `### Phase` grouping under `## Active sprint program: ...` whose final entry closes. Closing item 43 on 2026-05-08 collapsed the empty `### Sprint-tidy phase` header alongside the bullet; the next pickup line in the active-sprint header is the canonical "what to work on next" surface, not the phase headers.
- P2 conditional items framed "promote / add / land X only if Y shows up in a future refresh" sometimes have an unfireable trigger by construction. Before re-checking the trigger on the latest data, ask whether Y CAN happen at all. Hard-constraint predicates enforced post-condition by `solver-core/src/validate.rs`'s validator quintet (full list in `solver/CLAUDE.md` under "Post-condition validators quintet") surface as `Err(Error::Input)` (panic-cell rows in BENCH_RESULTS.md), not as `Violation` entries with a non-zero count, so a "non-zero count" trigger is structurally foreclosed and the right close is wontfix-by-construction with the closing commit citing the validator path. Item 43's `room_hop` axis was the exemplar; future `validate_*`-enforced predicates inherit the same shape.

**`DONE_WITH_CONCERNS` triage.** If a subagent reports `DONE_WITH_CONCERNS` and the concern is in-scope (perf-budget regression on a solver task, an unfixed lint, a missing test the spec required), fix it before committing, either in the main session or by re-dispatching with the gap added to the acceptance criteria. Do not carry the concern into the PR. For algorithm-phase work specifically, include the BASELINE.md 20% regression budget as an explicit acceptance criterion in the subagent prompt so the agent knows to optimise within its own task rather than surface the breach.

**Backend-driven `fe:types` regen requires `mise run fe:typecheck` before commit.** When an autopilot task adds, removes, or makes-required a field on a backend Pydantic schema and the next plan step is `mise run fe:types`, follow the regen with `mise run fe:typecheck` (which wraps `pnpm -C frontend run typecheck`, i.e. `tsc --noEmit`) before staging the commit. `mise run lint` runs biome only; biome does NOT type-check, and Vitest's esbuild type-stripping does NOT either. Pre-push (`.config/lefthook.yaml`'s `typecheck-frontend` slot) is the local fallback; CI's `Frontend CI / Lint + test + build` is a required status check on master, so a tsc-red push will not auto-merge. The local rule is the fastest feedback loop; the gates are belt+suspenders. Surfaced 2026-05-10 closing OPEN_THINGS item 69 when adding `PlacementResponse.teacher_id: UUID` (non-null) made five test-mock literals red against the regenerated types; biome + Vitest passed locally, lint passed locally, the PR auto-merged, and a hotfix PR followed. Trap closed in `fix(ci): close typecheck-not-required trap`.

**Module-deletion commits sweep stale doc-comment references in production source.** When a commit deletes a Python module (`refactor: delete dead X module + tests`), the deletion subagent's verification step `rg -n 'X' backend/src/` typically returns matches in unrelated production source files (model docstrings, seed comments) where prior commits documented the deleted symbol's role. Fold those doc-comment edits into the same commit, since they describe a symbol that no longer exists; do NOT touch xfail `reason=` strings inside test files (those are historical anchors that the matching test-refit item will rewrite when the xfail comes off), alembic migration docstrings (immutable history), or `CLAUDE.md` (the improving-instructions step at autopilot step 6 owns that surface). Path: edit the in-scope production references, `git add` only those files, `git commit --amend --no-edit` so the structural-deletion commit ships clean. Surfaced 2026-05-10 closing OPEN_THINGS item 69 when the Task 1 subagent flagged stale references in `db/models/scheduled_lesson.py` and `seed/demo_grundschule_dreizuegig.py` via `DONE_WITH_CONCERNS`.

**Upstream-state check on tool-named P0 spikes.** When a P0 OPEN_THINGS item names a specific external tool (Timefold, Choco Solver, OptaPlanner successor, etc.), do a quick PyPI / GitHub status check before brainstorming the integration path. Upstream archive status, Python-version compatibility against `mise.toml`'s pin, and EOL signals can flip the spike's outcome from "integrate" to "document and reject with concrete reasons". Item 55 (ADR 0035) flipped to rejection because Timefold's Python binding was archived 2025-10-06, supports Python 3.10-3.12 only (we pin 3.14.2), and the Java path violated the item's "bounded spike, do not let this become a product rewrite" framing.

**Bench-surfaced bug mid-run: ship the data, file a follow-up item.** When a production-budget `bench:bakeoff` refresh exposes a new solver bug (e.g. item 73's unpinned LAHC cells panicking on FFD greedy double-booking), the panic rows ARE legitimate refresh signal: they document the cost-of-widening (or whatever axis the refresh exercised), the bench supervisor handles panicked cells gracefully via `write_error_row` (renders `panic` in the Feasibility column and `-` in every numeric column), and the cells exit fast so the wall-clock cost is bounded. The right move is (a) let the bench finish, (b) commit `BENCH_RESULTS.md` including the panic rows, (c) file a new OPEN_THINGS item for the bug at the priority warranted (P0 if it blocks downstream items like the integration-test xfail removals), (d) update dependent items' bodies in the same OPEN_THINGS commit to route through the new follow-up (e.g. "blocks items 11, 14, 47, 72" on the new item, and "blocked by item N" on each of those). Do NOT stop the bench, fix the bug in the same PR, and re-run from scratch unless the user explicitly asks; that conflates structural and behavioural work and wastes the wall-clock already paid. Surfaced 2026-05-11 closing item 73 and filing item 74 (FFD picker double-booking under widened candidates).

**OPEN_THINGS item bodies are hypotheses, not ground truth.** When a P0 bug item names a suspected mechanism (e.g. item 74 said "FFD greedy double-booking under widened candidates" and pointed at `try_place_block`), treat that narrative as the *symptom* description, not the *cause*. The RED reproducer in the plan's RED phase is the source of truth; let the test fail, read the actual stack, and follow the call chain from there. Item 74's actual bug was in `try_place_group`'s static-teacher feasibility check plus three post-solve readers (`validate_no_double_booking`, `score_solution`, `quality_report`) consuming `lesson.assigned_teacher_id()` instead of `Placement.teacher_id`; `try_place_block` was already correct. Practical consequence for plans: phrase the GREEN-phase tasks as "make the RED test go green", not "edit `<suspect_function>`", and budget the diagnosis step explicitly so a subagent on Task 1 can pivot when the symptom narrative misnames the site. Surfaced 2026-05-11 closing item 74.

**Smoke bench validates fixes; production refresh refreshes data.** The dev-loop bench downscale (`mise run bench:bakeoff -- --budget 5s --seeds 1 --fixtures grundschule --teacher-pins off`, ~30 s wall-clock) is sufficient to validate a fix end-to-end when the bug shape is "every LAHC cell panics" or "every cell emits a specific violation kind". The 5-6 h production refresh is for refreshing the comparable artifact across (un)pinned variants in `BENCH_RESULTS.md`, not for proving a fix works. Don't gate the PR on the production refresh when the smoke is structurally conclusive; fire the production refresh in `run_in_background` and let it complete on its own schedule. Surfaced 2026-05-11 in item 74: the unpinned smoke at 5 s × 1 seed × grundschule showed every LAHC cell feasible post-fix (vs panic pre-fix), the PR shipped, and the supervised production refresh updated `BENCH_RESULTS.md`'s unpinned section asynchronously.

**Integration-test xfail-removal items: gate on the integration-test flake-loop, not the bench-data narrative.** When an OPEN_THINGS item names an integration-test xfail removal as the deliverable and cites bench data as the unblock proof ("items X / Y / Z shipped, bench cells 20/20 quality 4/4, this item is now unblocked"), the actual gate is a 20-iteration flake-loop on the integration test at its production wall-clock budget, NOT the bench narrative. The bench fixture pins teachers via `_TEACHER_ASSIGNMENTS_*` (per `backend/CLAUDE.md`'s "pin teacher allocation in seed solvability tests" rule); integration tests on the solver-driven teacher path go through `POST /generate-lessons` which leaves `Lesson.teacher_id` null and lets the solver pick from `teacher_candidates`, a strictly larger search space. The bench's `Quality (pass / 4)` on the pinned cell does NOT predict pass on the unpinned-cell integration test (already documented in `solver/CLAUDE.md`); upstream "now unblocked" claims in OPEN_THINGS items are hypotheses that the flake-loop verifies or denies. A **single-seed smoke bench `feasibility 1/1 hard_med=0` on an unpinned cell ALSO does not predict 20-iteration flake-loop stability:** item 11's 5 s × 1 seed × `lahc_rr` smoke landed feasible on both zweizuegig + dreizuegig unpinned cells, but the 20-iteration test at production `solve_deadline_ms=5000` showed 7/20 and 12/20 RED respectively with `teacher_over_capacity` dominant. Single-seed feasibility is a necessary but insufficient signal; the flake-loop is the only gate that catches non-determinism in the picker. Escalation when the flake-loop denies the hypothesis: ship commit 1 (the GREEN tests' xfail removals + rewritten reasons on the RED tests in one commit) AND the OPEN_THINGS update routing the RED measurements through an existing-axis item or a fresh item, then file the new OPEN_THINGS item at the priority warranted (P0 if it blocks downstream xfail-removal items), update the original item's body to reflect "partial close, remaining tests blocked by item N", and restore any forward-looking references in sibling items that the optimistic close-plan was going to drop. Surfaced 2026-05-11 in item 11 (round 1): OPEN_THINGS item 11 said items 73 / 74 / 75 unblocked the rename + xfail removal; the einzügig flake-loop produced 20/20 xfailed runs panicking on the LAHC `canonical_score == score_solution(...)` debug_assert (item 52's drift detector), which item 76 now tracks. Surfaced again 2026-05-12 in item 11 (round 2): post-item-78 the einzügig test went 20/20 GREEN but zweizuegig + dreizuegig stayed RED on a NEW mechanism (solver teacher-picker over-allocation), filed as item 79; partial-close shape worked exactly per this rule.

**Xfail-removal procedural shape: edit the test file first, then measure, then commit-or-revert.** For an OPEN_THINGS item that names an integration-test xfail removal as its deliverable, apply ALL GREEN-branch edits to the test file (delete the `@pytest.mark.xfail` decorator, raise the in-test `monkeypatch.setattr(app.state.settings, "solve_deadline_ms", ...)` to the production budget, refresh any module docstring naming the prior budget) BEFORE running the flake-loop. Then run the 20-iteration loop on the post-edit file with `-v --no-header` and NO `--runxfail` (the decorator is already gone), counting `^=+ 1 passed in` / `^=+ 1 failed in` summary lines via `grep -cE`. GREEN (zero failed iterations): commit as-is, the working tree is already commit-ready. RED (any failed iteration): `git checkout -- <test-file>` to discard the edits, then file the follow-up via the denial-and-reroute rule below. The alternative shape ("monkeypatch-only edit at 5000 ms → loop with `--runxfail` → branch → re-edit") forces the gate to count under TWO different pytest result states (`xpassed` pre-decorator-removal vs `passed` post) and requires a second edit pass on GREEN; the edit-first shape is one pass with one result state. Surfaced 2026-05-12 closing item 14 (20/20 PASSED at 5000 ms post-item-57; the edit-first shape collapsed plan tasks 2.1 + 4.1 into one).

**Flake-loop denial: reroute through an existing item when the failure axis matches.** When the flake-loop denies an xfail-removal hypothesis AND the failure shape's predicate + axis matches the planned closure surface of an ALREADY-OPEN OPEN_THINGS item, do NOT file a duplicate bug item. Reroute instead: in one docs-only commit, (a) rewrite the xfail item's body with the measurement (count, predicate, failing axis values, exemplar QualityIssue dict), (b) invert the dependency in the receiving item's body if it had a "land after item N" or similar precondition — mark the trigger SATISFIED, drop the "land after" line, note that the original item is now blocked by this one, (c) refresh any acknowledged-deferrals or sprint-motivation anchors that reference the original dependency direction. Reroute applies ONLY when the failure axis is the same as the existing item's planned optimisation surface; if the failure is a NEW mechanism (panic class, validator violation, soft-cost predicate nobody is tracking), file a fresh OPEN_THINGS item per the rule above. Surfaced 2026-05-12 closing the item 14 flake-loop measurement: 3/20 RED with `check_class_day_balance` `spread=3-4 > max_spread=2`, matching item 57's "widen the canonical objective to bound per-class worst-case quality bars" surface exactly; rerouted via `docs(open-things): item 14 flake-loop measurement reroutes through item 57` (commit 51b3bb7).

**Plan-time existence check on every test file the plan touches.** Before writing a plan task that says "extend `frontend/src/features/<area>/<name>.test.tsx`", `ls` it. The frontend mixes two test-locale conventions: feature-local specs (e.g. `school-classes-dialogs.test.tsx`, `rooms-dialogs.test.tsx`) AND `frontend/tests/`-level page tests (e.g. `teachers-page.test.tsx`). The presence of `<feature>/<dialog>.tsx` does NOT imply the existence of `<feature>/<dialog>.test.tsx`; `teachers-dialogs.test.tsx` did NOT exist on master when item 71's plan first listed it as "Modify". When the file is missing, the plan must explicitly say CREATE, name the canonical sibling test file to mirror (`school-classes-dialogs.test.tsx`'s `wrapSchoolClassDialog` `QueryClientProvider` pattern is the closest current reference), and account for stubbing any sub-components the dialog mounts only in EDIT mode (e.g. `TeacherQualificationsEditor` + `TeacherAvailabilityGrid` need their endpoints stubbed via `server.use(...)` overrides so `onUnhandledRequest: "error"` doesn't fire). Surfaced 2026-05-10 in item 71 when the plan reviewer flagged the missing `teachers-dialogs.test.tsx` as a blocking issue. Same shape applies to `useStundentafel` / `useWeekSchemeDetail` / any other `enabled: id !== null` hook called from a form-watcher: the `id || null` coercion rule lives in `frontend/CLAUDE.md`; the plan should reference it when the picker's selected entity drives a follow-up detail query.
