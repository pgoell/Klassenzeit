# Klassenzeit: Solver Rules

Applies to the `solver/` Cargo workspace (`solver-core` + `solver-py` + `solver-bench`). Assumes the cross-cutting rules in the root `.claude/CLAUDE.md` (no bare catchalls, unique function names, no dynamic imports, Dockerfile context rules, SHA-pinned third-party actions, Conventional Commits).

## Workspace layout

- **`solver-core`**: pure Rust library. The scheduling algorithm, constraint model, and typed errors live here. No PyO3, no Python, no I/O beyond what callers pass in.
- **`solver-py`**: `cdylib` crate that wraps `solver-core` via PyO3 (`0.28`) and is built by maturin into the `klassenzeit_solver` Python package. Thin wrappers only; no algorithm logic.
- **`solver-bench`**: Rust binary crate that runs the solver feasibility bake-off. Imports `solver_core::test_fixtures` (gated behind default-on `fixtures` Cargo feature; solver-py opts out via `default-features = false`). Single `src/main.rs`, manual CLI parsing, no external runtime deps. ADR 0029.
- **Root `Cargo.toml`**: workspace root. Declares `edition = "2021"`, `rust-version = "1.85"`, `resolver = "2"`. Shared dev-dependency: `proptest = "1"`. All three crates inherit via `[workspace.package]` / `[workspace.dependencies]`.
- **Root `pyproject.toml`**: uv workspace. `solver/solver-py` is a member; backend pulls it in via `klassenzeit-solver = { workspace = true }`.
- **Hand-maintained `.pyi` stubs**: `solver/solver-py/python/klassenzeit_solver/*.pyi`. Updated in the same commit as a Rust binding change.

## solver-core rules

- **`#![deny(missing_docs)]` is on at the crate root.** Every new `pub` item, including struct fields, enum variants, and macro-generated newtypes, needs a `///` rustdoc line or the crate refuses to compile. Plans that paste ready-to-compile code must include the doc comments.
- **`clippy::doc_lazy_continuation` flags `+` at the start of a `///` continuation line** as a Markdown bullet against the previous line and fails the `-D warnings` build. Use `and` / `plus` instead, or indent the continuation by two spaces.
- **Errors use `thiserror`, one enum per logical boundary** (input parsing, constraint validation, scheduling). No `anyhow` in `solver-core`; a library erases type information when it boxes, and the backend wants to match on specific failure modes.

    ```rust
    #[derive(Debug, thiserror::Error)]
    #[non_exhaustive]
    pub enum Error {
        #[error("input: {0}")]
        Input(String),
    }
    ```

- **Deterministic under test.** No `std::time::SystemTime::now()` inside `solver-core`; no `rand::thread_rng()`. Any randomisation is seeded via a parameter on the public API so tests reproduce. Non-determinism here is silent (unit tests pass for a specific seed) and only surfaces as run-to-run timetable drift. `solver-py` is allowed to wrap the deterministic core with wall-clock timing for logging.
- **Tests.** Inline `#[cfg(test)] mod tests` for unit, `solver-core/tests/*.rs` for integration (property tests, multi-step scenarios). When a shared fixtures module grows, add `solver-core/tests/common/mod.rs`.
- **Property-test generator widenings need a 5x128 local sweep before commit.** When you change a `prop_compose!` block (draw a new field, widen a range, raise an enum's variant count), CI's committed `cases:` setting (typically 32) can leave a code path uncovered for many seeds. Run `for s in 1 2 3 4 5; do PROPTEST_CASES=128 PROPTEST_SEED=$s cargo nextest run -p solver-core --test <file>; done` from the repo root to validate the widened generator actually exercises the path you claim. Failed seeds get pinned in `tests/<file>.proptest-regressions` and replay deterministically. When generator inputs have divisibility constraints (e.g. `validate_structural` requires `hours_per_week % preferred_block_size == 0`), construct values from a formula in the closure rather than `prop_assume!`-filtering, since proptest's shrink rejects assumed-out cases aggressively. Sprint item 40's `lahc_small_problem` widening is the canonical example.
- **Bench targets cannot host libtest tests.** A `[[bench]] harness = false` binary (criterion's requirement) runs criterion's `main()`, not libtest; inline `#[cfg(test)] mod tests { #[test] fn ... }` inside the bench compiles but its `#[test]` functions never execute. Put the helper plus its tests in a dedicated `benches/<name>.rs`, then `#[path]`-include that file from both the bench target and a one-line `tests/bench_<name>.rs` integration binary so libtest picks the tests up (`solver-core/benches/percentile.rs` + `solver-core/tests/bench_percentile.rs` are the template).
- **Lowest-delta greedy iterates pre-sorted indices.** `solve_with_config` sorts `time_blocks` by `(day_of_week, position, tb.id)` and `rooms` by `id` once per solve, then iterates index lists. The picker's `(score, day, position, room.id)` tiebreak rule and its early-exit at `score == state.soft_score` both depend on those orderings. PR-9b's LAHC neighbour generator must reuse the same orderings or the solver loses run-to-run determinism that the property test in `tests/score_property.rs` enforces.
- **Soft-score evaluation must not allocate inside `try_place_block`.** The candidate-scan is `O(time_blocks * rooms)` per placement; an early version of `gap_count_after_insert` cloned the partition `Vec<u8>` per call and breached the 20% bench budget ~17x on `zweizuegig`. The non-allocating shape (compute `new_min`/`new_max`/`len_after` from the existing `&Vec<u8>` plus the proposed `pos`, then call `score::gap_count`; for n-block windows use `gap_count_after_window_insert`) is the canonical pattern; LAHC's delta evaluation follows the same shape.
- **`try_place_block`'s picker scores by total (slice + home_room_penalty), persists slice.** The room scan tracks the minimum-`home_room_penalty(room)` feasible room with strict `<` and a `penalty == 0` early-break (when a home-room match exists at low id, later rooms are id-greater and at-best-tied so cannot strictly beat it). `BlockCandidate` carries both `slice_score` and `total_score`; window-level pruning compares on slice (lower bound on total since `home_room_penalty >= 0`) so the existing pruning stays sound. The persist site stores `slice_score` into `state.soft_score`, holding the slice contract LAHC's Change move and R&R's `running_slice_from_placements` recompute rely on. Mixing `home_room` into the persisted score would contaminate the slice and trip `try_change_move`'s non-negative-delta debug_assert. Pinned by `try_place_block_room_picker_minimises_home_room_penalty` (picker level) and `lahc_rr_recreate_picks_lowest_soft_delta` (R&R end-to-end) plus the fall-back determinism test `try_place_block_room_picker_falls_back_to_id_order_when_no_home_room_advantage` (strict `<` does not flip on a 0 == 0 tie).
- **Per-iteration `debug_assert_eq!(running_X, full_recompute_X)` catches incremental-delta drift.** When you add an incrementally-maintained running total to LAHC's hot path (slice + delta, canonical + delta, partition gap counts + delta), gate correctness on a `#[cfg(debug_assertions)]` `debug_assert_eq!(state.<running>, <full_recompute>(...))` at the LAHC iteration tail. Any per-move delta arithmetic bug (mismatched signed widths, missing class in a sum, off-by-one on integer division, omitted axis on a new move type) surfaces instantly under any property test or unit test that exercises `lahc::run`; release builds compile away. Used by the `canonical_score` maintenance in item 52; the same shape extends to any future running cost dimension. Combine with a `for s in 1 2 3 4 5; do PROPTEST_CASES=128 PROPTEST_SEED=$s cargo nextest run -p solver-core --test lahc_property; done` sweep to cover seed space the committed `cases:` setting misses.
- **Per-class-max canonical axes use temp-swap delta in Change move, full recompute in Kempe, and ride R&R's existing recompute.** When an additive `canonical_score` summand is "max over classes of f(class, placements)" (item 57's `worst_class_spread`, `worst_class_interior_gaps`), the Change-move delta is implemented by temp-swapping `placements[idx].time_block_id` to the candidate TB, calling the helper, swapping back, and bracketing pre/post values into `canonical_delta`. Kempe snapshots the pre-attempt weighted cost at the top of `kempe_attempt`, recomputes post-apply from the mutated `placements`, folds delta into `canonical_delta` (full-recompute pattern; throughput trade-off is bench-validated). R&R already calls `state.canonical_score = score_solution(...)` post-recreate so the new axis flows through automatically. The temp-swap shape works iff the helper depends only on `Placement.time_block_id` (via `tb_lookup`); a helper reading `room_id` or `teacher_id` needs a multi-field temp-swap. The per-iteration `debug_assert_eq!(state.canonical_score, score::score_solution(...))` gate catches delta-arithmetic drift instantly under any test that exercises `lahc::run`. Surfaced 2026-05-12 closing OPEN_THINGS item 57.
- **`GreedyState` carries two scores: `search_score_slice` and `canonical_score`.** The slice (`class_gap + teacher_gap + subject_pref`) is the LAHC search-time hot-path objective: greedy's `try_place_block` picker persists slice into `state.search_score_slice`; the Change-move non-negative-delta `debug_assert!` checks slice; `running_slice_from_placements` recomputes slice for R&R; Kempe's snapshot+delta walks slice. The canonical (full `score_solution`, slice plus `prefer_home_room` plus `class_day_balance`) is the LAHC accept-time objective: `lahc_list` stores canonical; the accept criterion compares canonical against current and prior; `time_to_optimal_ms` fires on canonical improvement; the early-exit predicate's canonical half fires at `state.canonical_score == 0` (the predicate is conjunctive on placement count, see the "LAHC outer loop exits at the conjunctive objective floor" rule below). Both fields are maintained in lockstep across all three moves (Change via incremental delta, R&R via full `score_solution` recompute, Kempe via snapshot plus delta extension to per-class day-counts and per-row home_room contributions). Changes that touch one score must keep the other consistent or the per-iteration `debug_assert_eq!(state.canonical_score, score::score_solution(...))` in test builds will fire. Item 52.
- **LAHC RNG draw count must be invariant across loop branches.** The determinism property test in `solver-core/tests/lahc_property.rs` relies on every iteration consuming exactly two `random_range` calls (placement_idx, new_tb_idx) regardless of feasibility outcome. Conditional `random_range` calls inside the LAHC loop, e.g. an extra draw on a feasibility-failure path, break determinism silently, surfacing only as a flaking property test under fixed seed plus iteration cap.
- **R&R uses a separate `SmallRng` seeded from `config.seed.wrapping_add(1)`.** The Change-move RNG sequence remains byte-identical to today's; the existing determinism property test (`lahc_property::lahc_deterministic_under_seed_and_iter_cap`) passes unchanged. R&R does not consume from the Change-move RNG even on R&R iterations, so the two-`random_range` invariance applies only to Change iterations. Determinism for R&R-enabled solves is guaranteed by the dedicated R&R RNG plus the per-iteration scheduling (`iter % rr_period`).
- **R&R move semantics.** Block-level ruin (a Doppelstunde lesson is ruined as one N-block, never half), skip pinned lessons, skip lesson-group members. Recreate calls `crate::solve::try_place_block` against the ruined bookkeeping; on any recreate failure the move is rolled back to the pre-attempt snapshot. Acceptance gate is asymmetric: reject on any `failed_recreates > 0`, otherwise standard LAHC criterion on `state.soft_score`. `rr_attempt` handles the ruined-only path; `rr_rescue_attempt` (item 78, shipped 2026-05-12) handles FFD-unplaced lessons by ruining ALL of the under-placed target's existing placements plus one randomly-chosen same-class sibling anchor, then re-placing the target from scratch and recreating the sibling block. Lesson-group targets dispatch to `rr_rescue_group_attempt`, which ruins every member's placements and re-places via `try_place_group` (visibility bumped to `pub(crate)` in the same commit). Rescue's accept gate is feasibility-only: target's placement count strictly increased AND sibling block fully recreated. Each R&R iteration calls rescue first; if rescue aborts (no under-placed lesson, no eligible sibling) or rejects, the iteration falls through to `rr_attempt`. Both consume from the shared `rr_rng` (`config.seed.wrapping_add(1)`); rescue's two RNG draws are unconditional across abort branches.
- **`score::score_solution` does NOT include hard violations.** Adding a placement strictly INCREASES canonical because it adds more partition contributions (class_gap, teacher_gap, class_day_balance, prefer_home_room, late-period axes). A feasibility-restoring LAHC move (item 78's rescue, any future Kempe-rescue or similar) therefore raises canonical even when it removes a hard violation, the opposite of what naive "removing hard violation improves canonical" reasoning predicts. Practical consequences: (a) the LAHC running-best snapshot in `lahc::run` MUST be lexicographic on `(placements.len() desc, canonical asc)`, NOT canonical alone, or feasibility-restoring accepts get discarded at loop exit's `*placements = best_placements` because canonical rose. The track variable is `running_best_count` paired with `running_best`; both update atomically when either dimension strictly improves. (b) Rescue's accept gate cannot lean on canonical-score comparison; use a direct feasibility check (`target_count_after > target_count_before` plus `sibling_fully_recreated`) instead. Same shape applies to any future move that lifts feasibility from a partial state. Surfaced 2026-05-12 closing OPEN_THINGS item 78.
- **Post-LAHC violations filter in `solve_with_config_stats`.** FFD's `try_place_block` emits one violation row per unplaced hour (`NoFreeTimeBlock` / `TeacherOverCapacity` / `NoSuitableRoom`), and `try_place_group` emits `LessonGroupSplit` per failed atomic group placement. The `solution.violations` vec is FFD-static across LAHC: LAHC accepts mutate `placements` and `state` but do NOT touch the violations vec. When item 78's rescue lifts a lesson from under-placed to fully-placed, the stale FFD-time violation rows for that lesson would still ship out of `solve_with_config` unless cleared. The post-LAHC filter (in `solve.rs` between `lahc::run` and the post-condition validator quintet) drops `{NoFreeTimeBlock, TeacherOverCapacity, NoSuitableRoom, LessonGroupSplit}` rows whose lesson's post-LAHC placement count `>= hours_per_week`. Other variants (`NoQualifiedTeacher`, `PinnedConflict`, `*Exceeded`, `ClassSubjectTeacherSplit`) pass through verbatim. Any future feasibility-lifting LAHC move inherits the filter automatically; new violation kinds whose semantics are "FFD-time only" should be added to the filter's match arm. Surfaced 2026-05-12 closing item 78.
- **Rescue's anchor scope is target's-own-placements PLUS one same-class sibling.** Under unpinned mode (ADR 0036), FFD-unplaced lessons commonly hit `teacher_over_capacity` ceilings, not class-day ceilings. Ruining a same-class anchor of a DIFFERENT lesson frees class-day slots but leaves the target's `(class, subject)` teacher lock bound to a saturated teacher, so `try_place_block` re-picks the same teacher and the rescue fails. The fix: ruin ALL of the target's existing placements first (so the lock cleanup in the post-destroy walk clears the target's lock entry) PLUS one same-class sibling (to free additional class-day slots the target needs). `try_place_block` then re-picks a teacher with free capacity. Plan-time "ruin one anchor" framing under-budgets the rescue's actual scope; future feasibility-lifting moves should default to "ruin every placement of the target lesson" rather than "ruin one anchor" when the failure shape involves teacher-axis bottlenecks. Surfaced 2026-05-12 closing item 78.
- **`SolveConfig.lahc_rr_k` is the R&R chain-width knob.** Default `5`; controls the maximum number of block-anchors `rr_attempt` ruins per R&R iteration (`anchors.len().min(rr_k as usize)`). Tunable via `solver-bench --rr-k <csv> --rr-period <csv> --append` for sweep mode (item 21); the supervisor cross-products K and period over the `(fixture, backend)` grid for `lahc_rr` and `lahc_rr_kempe` cells, renders `RR_K | Period` columns plus a `## Pareto frontier` per fixture and a `## Recommendation` block. Non-RR backends (`lahc`, `lahc_kempe`, `cpsat`) render once per fixture with `-` sentinels. The recommendation block in `BENCH_RESULTS.md`'s `## RR sweep` sections is the canonical source for the production default; bumping the default is a one-line change to `SolveConfig::default().lahc_rr_k` in `solver-core/src/types.rs`. The bench dispatch in `solver-bench/src/main.rs` already falls back to `SolveConfig::default().lahc_rr_k` when no `--rr-k` override is given, so default-tracking bench cells swing with the bump automatically; no edit to the dispatch table is required.
- **Kempe move semantics.** Two-day same-position swap of a block-anchor: pick B1 at (D1, P1, N), pick D2 != D1, propose moving B1's window to (D2, P1..P1+N-1). BFS over the teacher+class conflict graph at the destination window builds the chain (rooms handled at apply); chain depth bounded at `config.lahc_kempe_max_chain` (default 8; promoted from the private `KEMPE_MAX_CHAIN` constant under OPEN_THINGS item 23, swept via `solver-bench --kempe-max-chain <csv>`). Block-aware (Doppelstunden swap atomically), pin-skip, lesson-group skip. Asymmetric acceptance: any chain-construction abort (over-bound, pin/group hit, missing window position) or apply failure (no feasible room, lock conflict) rolls back to the pre-attempt snapshot and rejects, otherwise standard LAHC criterion. Three-RNG split: Kempe uses a separate `SmallRng` seeded from `config.seed.wrapping_add(2)`, so the existing Change and R&R determinism property tests pass byte-identically. BFS new-neighbour set sorted by `LessonId.0` before extending the frontier to remove `HashSet` iteration non-determinism.
- **Kempe BFS must enforce bipartiteness of the chain conflict graph.** The BFS produces a 2-coloring assignment (`chain[seed] = dest_day`, even-depth members `dest_day`, odd-depth members `source_day`), but adjacent-pair conflict checks alone are not enough: a depth-2 chain member can share a class or teacher with the seed (or any other same-color member) and the BFS will silently accept the chain because the read-only `placements` view does not yet reflect the chain destinations. Per-edge same-color cross-check at the new-neighbour insertion site fixes it: when assigning `chain[candidate] = neighbour_dest`, walk every entry in `chain` whose value equals `neighbour_dest` and reject the chain if any of them shares a class or teacher with the candidate. The check uses `chain.iter().any(...)` over a `HashMap`; the result is a boolean so iteration order does not affect determinism. Bound `O(config.lahc_kempe_max_chain^2)` per BFS (default 64), negligible against the LAHC deadline. Same shape applies to any future BFS-based ruin+apply move: a 2-coloring without bipartiteness verification produces same-day same-class collisions caught only by the post-condition validators (item 45 was caught by `validate_no_double_booking` on grundschule at production budget). Pinned by `lahc_rr_kempe_does_not_double_book_class_at_grundschule` (targeted, seed 8) and `lahc_rr_kempe_does_not_double_book_class` (property) in `tests/lahc_property.rs`.
- **BFS-shaped move sites must read teacher via `lesson_teacher_in_state(state, lesson)`, not `lesson.assigned_teacher_id()`.** Once the solver picks teachers (item 68), the per-(class, subject) lock map in `state.class_subject_teacher` may bind a different teacher than `assigned_teacher_id()` returns (the latter falls back to `teacher_candidates[0]` when no `teacher_pin` is set). Any move-site teacher comparison that goes through the static lesson field misses lock-map-bound teachers and silently accepts chains that should be rejected as conflicts. `kempe_build_chain`'s two BFS conflict-detection sites (the popped-vs-new-neighbour check and the bipartiteness same-color cross-check) read `lesson_teacher_in_state(state, lesson)`; thread `state: &GreedyState` into any new BFS-shaped or ruin+apply move and route every teacher comparison that has NO captured row in hand through that helper. Rollback / row-removal paths are the exception and read `row.teacher_id` / `p.teacher_id` instead (see the rollback-read rule below); the boundary is "do you already hold the row you are reasoning about?". Latent failure mode: bench fixtures pin teachers via `_TEACHER_ASSIGNMENTS_*` so `assigned_teacher_id()` and the lock map agree; the bug surfaces only under unpinned solver runs (item 73's no-pinned bench refresh). Pinned by `kempe_build_chain_uses_lock_map_teacher_for_bfs_conflict_detection` in `lahc.rs::tests`.
- **`score_solution`'s per-class-day partition shape must match `state.class_positions`'s dedup'd shape.** `class_day_balance_cost` consumes `.len()` on each `by_class_day` vec (`score.rs:184-216`), so any axis aggregating per-(class, day) counts must dedup the vec before counting. `class_gap` already dedups via `sort+dedup` before `gap_count`, but `class_day_balance` walked the raw push count until item 76. Lesson-group co-placements (religion trios sharing one `(day, position)` slot) push 3 entries into `by_class_day` while `state.class_positions` keeps one (apply_change_move's insert-guard dedups). Mismatch surfaces as per-iteration `state.canonical_score` drift over Change-move iterations because LAHC's `class_day_balance_delta` reads the dedup'd partition while `score_solution`'s FFD seed reads the push-count partition. Same shape applies to `quality_report`'s `class_day_balance_cost` consumer. Fix is a single `sort_unstable + dedup` pass over `by_class_day.values_mut()` before invoking `class_day_balance_cost`; any future axis that reads partition counts via `.len()` (e.g. a hypothetical "lessons per day cap" soft penalty) inherits the same gate. Surfaced 2026-05-11 closing OPEN_THINGS item 76 on the dreizuegig unpinned grundschule fixture.
- **`test_fixtures::*_fixture()` builders set `class_teacher_id: None` on every `SchoolClass`.** All four bundled builders (`grundschule_fixture`, `zweizuegig_fixture`, `dreizuegig_fixture`, `gesamtschule_fixture`) leave `class_teacher_id` unset, so the `prefer_class_teacher` soft-cost axis is structurally inert in Rust integration tests built directly on them (the `class_teacher_lookup.get(cid) -> Some(Some(klt))` extraction in `score_solution` short-circuits and `prefer_class_teacher_misses` stays at 0). The backend `demo_grundschule_*` seed DOES set `class_teacher_id` per Hessen Klassenlehrer convention, so the axis is only exercised end-to-end via backend integration tests. A Rust regression test that wants to exercise the axis (e.g. item 76's second drift site) must explicitly stamp `class_teacher_id` onto each class after invoking the builder: pick any `TeacherId` from `problem.teacher_qualifications` qualified for one of the class's lesson subjects, then `class.class_teacher_id = Some(t)`. Pattern: `lahc_unpinned_test_assign_class_teachers(&mut problem)` in `solver-core/tests/lahc_unpinned_canonical_score.rs`. Surfaced 2026-05-11 closing item 76 (Rust regression at 3000 iters passed on dreizuegig with stamped class_teacher_ids; the backend integration tests at 5000 ms LAHC budget surfaced the same drift one bug deeper).
- **More LAHC teacher-key sites to audit for the lock-aware accessor.** Sibling to "BFS-shaped move sites" (item 73) / "Post-solve readers" (item 74) / "Row-based bookkeeping in rollback paths" (item 75): two MORE internal LAHC partition-key builders read `lesson.assigned_teacher_id()` and need the lock-aware accessor under unpinned mode. Both fixed 2026-05-11 closing item 76: `kempe_snapshot_pre_score` (Kempe's per-(teacher, day) partition snapshot consumed by `kempe_post_score_delta`'s soft-score delta arithmetic) and `running_slice_from_placements` (R&R's post-recreate slice recompute that partitions placements by teacher key). Both now route through `lesson_teacher_in_state(state, lesson)` and `p.teacher_id` respectively, mirroring the established pattern. Audit principle going forward: when grepping for `assigned_teacher_id`, do NOT restrict to "obvious move-site readers"; ALSO walk every LAHC-internal helper that builds a per-(teacher, ...) HashMap snapshot or partition. Each such helper is suspect because it mediates partition shape; a wrong teacher key snapshots the wrong partition and the delta arithmetic silently misses every subsequent change to the real teacher's slot.
- **Post-solve readers consume `Placement.teacher_id`, not `Lesson::assigned_teacher_id()`.** Sibling rule to the BFS-shaped-move rule above (and to the row-based rollback-read rule below, item 75's mid-solve equivalent), covering everything that reads a `Placement` after the solver picked its teacher. Sites: `validate_no_double_booking` (the teacher key in the per-(teacher, time_block) HashMap), `score_solution`'s `by_teacher_day` partition, `quality_report`'s `by_teacher_day` partition, `try_place_group`'s per-member feasibility/apply path. The pre-item-68 default `assigned_teacher_id()` returns `teacher_pin` when set and `teacher_candidates[0]` otherwise; under widened candidates (`solver-bench --teacher-pins off`, the solver-driven assignment path per ADR 0036), two placements made with distinct picker-chosen teachers can collide on the same static fallback, producing a false-positive `validate_no_double_booking` panic (bench failure mode) or a wrong-teacher `teacher_gap` aggregation (silent soft-score drift). Fix per site: replace `lesson.assigned_teacher_id()` with `p.teacher_id` (the field the picker stored). Pinned mode is byte-identical (`assigned_teacher_id() == p.teacher_id` when `teacher_pin = Some(t)`); only unpinned mode shifts. Pattern surfaced 2026-05-11 closing OPEN_THINGS item 74. Same shape applies to any new post-solve consumer (e.g. `class_teacher_subject_share` predicate, item 72): start from `p.teacher_id`, not `lesson.assigned_teacher_id()`. Pinned by `ffd_greedy_on_grundschule_unpinned_does_not_double_book` in `solver-core/tests/picker_no_double_book.rs` and the unpinned bench refresh's feasible LAHC cells.
- **Pre-solve seed sites consume `pin.teacher_id` (or `pl.teacher_id` from the seeded `Placement`), not `Lesson::assigned_teacher_id()`.** Sibling to the post-solve-readers rule above, but on the OTHER side of the solve. Sites: `validate_pins` stamps each seed `Placement.teacher_id` from `pin.teacher_id.unwrap_or_else(|| lesson.assigned_teacher_id())`; `seed_greedy_state_from_pins` populates FOUR `state.*` maps from `pl.teacher_id` (`state.used_teacher`, `state.hours_by_teacher`, `state.class_subject_teacher`, and the easy-to-miss-fourth `state.teacher_positions`). The `PinnedPlacement` wire format carries `teacher_id: Option<TeacherId>` (item 77) with `#[serde(default)]` so legacy callers fall back; backend `collect_pinned_placements` / `collect_own_class_pins` / `collect_all_pins` populate it from `ScheduledLesson.teacher_id` so the per-class-sequential `/schedule` flow's pins reflect the picker's real teachers. The latent failure mode pre-item-77: under unpinned mode (ADR 0036), two prior-class pins sharing `teacher_candidates[0]` collapse the seed to the same pseudo-teacher and `validate_no_double_booking` rejects the output with `input: double-booking`. Surfaced 2026-05-11 closing OPEN_THINGS item 77. Audit principle going forward: when adding a new `state.*` map keyed by teacher to `seed_greedy_state_from_pins` (or any pre-solve seed function), route through `pl.teacher_id`; a `grep -n 'lesson.assigned_teacher_id\|lesson\.assigned_teacher_id' solver/solver-core/src/solve.rs` should return zero hits inside `seed_greedy_state_from_pins`'s body. This guarantees both `solution.placements.len() >= greedy_solution.placements.len()` (item 78 rescue cannot regress feasibility) and `solution.soft_score <= greedy_solution.soft_score` (item 52 wandering-current guard). Pinned by `lahc_canonical_score_is_non_increasing_versus_greedy_under_production_weights` in `tests/lahc_property.rs`. Items 52 + 78.
- **Post-condition validators quintet.** `solver-core/src/validate.rs` hosts five checks that `solve_with_config` runs on the final placements vector: `validate_no_room_hopping` (same-room invariant), `validate_daily_caps` (Subject and SchoolClass per-day caps), `validate_no_double_booking` (class / teacher / room non-overlap + lesson cardinality + block shape), `validate_placement_teacher_in_candidates` (every Placement.teacher_id is in the corresponding Lesson.teacher_candidates and matches teacher_pin when set, item 65), `validate_class_subject_teacher_uniformity` (every `(SchoolClass, Subject)` pair has at most one distinct teacher across placements, item 66). Wiring pattern is identical: one release-mode `Result`-form call per validator at the tail of `solve_with_config_stats`; `Err(Error::Input)` propagates via `?` and integration tests `.expect()` it. Validator failures indicate a solver bug, not malformed input. New post-condition validators should follow the same shape (one fn, one walk over `placements`, sibling tests inline in `validate.rs::tests`).
- **Placement struct-literal sites in unit tests bypass the post-condition validator chain.** `score.rs`, `quality.rs`, and `validate.rs` unit tests construct `Placement { ... }` directly to feed local pure functions (`score_solution`, `validate_no_double_booking`, `validate_daily_caps`, etc.) rather than going through `solve_with_config_stats`. Adding a new Placement field with a stricter post-condition (e.g. item 65's `teacher_id` plus `validate_placement_teacher_in_candidates`) is therefore safe with placeholder values (e.g. `TeacherId(Uuid::nil())`) at those sites; the new validator only runs inside `solve_with_config_stats`, where Placements come from the algorithm sites you patched. This keeps the cascade tractable: only algorithm sites (FFD greedy in `solve.rs`, R&R recreate / Change move / Kempe apply in `lahc.rs`) need real `lesson.assigned_teacher_id()`-equivalent values; pure-function unit tests use placeholders. Surfaced 2026-05-08 implementing item 65.
- **Validator cardinality is `>` only (over-placement), not `!=`.** `try_place_block` may fail and emit `Violation::NoFreeTimeBlock` / `NoSuitableRoom` / `TeacherOverCapacity` per missing hour; under-placement is legal solver output detected upstream via the violations vec and the bake-off bench's per-cell placement-count gate. `validate_no_double_booking` initially used `!=` and broke 16 existing tests including `solve::tests::block_lesson_emits_one_violation_per_failed_block` (4-hour lesson placing 2 hours and emitting one violation). New post-condition validators must mirror this contract.
- **`validate_no_double_booking` exempts lesson-group co-placement from the class check.** Two lessons sharing a `(class, time_block)` pair are accepted iff both have the same `Some(lesson_group_id)` (per-Jahrgang religion trio: students pick one of RK / RE / ETH). `try_place_group` co-places all members at one `(day, position)` window in the same class set; the validator must not flag this. Teacher and room collisions remain hard violations regardless of group: a teacher cannot teach two lessons at once, and `try_place_group`'s `taken: HashSet<RoomId>` already forbids two members from sharing a room. Pattern surfaced when the dreizügige fixture's religion trio tripped the validator on FFD greedy output, before LAHC ever ran.
- **`try_place_block` has three callers, not two.** `solve.rs::solve_with_config_stats` (FFD greedy lesson loop) and `lahc.rs::rr_attempt`'s recreate phase both invoke it as production code; `solve.rs::tests` has two unit-test invocations. Plans that estimate "two call sites" for a signature change miss `lahc.rs`; budget the cascade. Sister rule for `try_place_group`: only one production call site (the FFD greedy lesson-group branch in `solve.rs`), no R&R or LAHC consumer today.
- **FFD picker's first-pick capacity check requires whole-lesson hours, not block n.** When `existing_lock.is_none() && lesson.teacher_pin.is_none()` in `try_place_block` (and the symmetric `!is_locked && member.teacher_pin.is_none()` in `try_place_group`), the candidate's capacity gate must be `current + lesson.hours_per_week > max`, not `current + n > max`. The first placement creates a `class_subject_teacher` lock that collapses every subsequent block of the same `(class, subject)` to the same teacher; picking a teacher who can only fit the FIRST block locks the lesson to a teacher who fails on subsequent blocks, producing a stream of `TeacherOverCapacity` violations that LAHC R&R rescue cannot always recover within the production budget. After the lock exists, the per-block ceiling `n` is the correct contract because candidates collapse to the locked singleton. Pinned by `solver-core/tests/picker_teacher_capacity.rs::ffd_greedy_on_dreizuegig_unpinned_does_not_over_allocate_teachers` (item 79). Same axis as item 80 (FFD lesson-ordering myopia) is still open: the picker-capacity check is necessary but not sufficient when FFD's lesson order exhausts all qualified candidates BEFORE reaching a hard lesson.
- **Multi-bug fixtures: measure master-HEAD residuals before writing a strict feasibility assertion on a new Rust integration test.** A test that asserts `solution.placements.len() == expected_total_hours` on `dreizuegig_fixture` under `unpin_teachers` will fail on master HEAD with a mix of `TeacherOverCapacity` AND `LessonGroupSplit` violations; the latter is FFD search-myopia on religion-trio co-placement (LAHC R&R rescue handles it at production budget, but `max_iterations: Some(0)` exercises only FFD). When a new RED test asserts strict feasibility, run a probe-bin or one-off `solve_with_config` on master HEAD first to enumerate the residual violation kinds; then either write the assertion to exclude pre-existing residual kinds (`placements + lesson_group_split_count >= expected`) or scope the test to FFD assertions independent of placement count. Pattern surfaced 2026-05-12 in item 79's RED test: initial assertion `placements.len() == 294` blocked the fix commit at the secondary assertion because the 3 religion-trio `LessonGroupSplit` hours predated item 79. Same shape applies to any future picker / ordering / capacity fix that sets up its RED on a fixture with multiple co-existing FFD-time gaps.
- **`try_place_block`'s window-level picker uses strict `<` end-to-end.** Both the room scan within a window (lowest `home_room_penalty` wins, lowest `room.id` on tie via `room_order`'s id sort) and the cross-window comparison (lowest `total_score` wins, lowest `(day, position, tb_id)` on tie via `tb_order`'s sort) resolve ties to the FIRST-walked candidate. The pruning bound `if slice_score >= b.total_score { continue; }` filters which windows are considered before the comparison runs; among the survivors strict `<` keeps the FIRST-walked candidate. Item 60 brought the cross-window site in line with the room scan; before item 60 the cross-window assignment was unconditional and the LAST-walked feasible candidate won on tied `total_score`. Targeted picker tests can now assert exact `(day, position)` outcomes on tied candidates as long as `tb_order` is the canonical sort.
- **Pre-merge smoke bench: dev-loop downscale (`--budget 5s --seeds 4 --fixtures grundschule,zweizuegig`, ~30 s wall-clock).** Same downscale recipe documented in the bench section below; the framing here is "use it before pushing", not just "use it for inner-loop iteration". Reports per-cell feasibility, worst_spread, soft_med, quality_med across the LAHC variants and is the right gate before opening a PR; the production-shape refresh stays post-merge. CP-SAT cells fail with `ModuleNotFoundError` unless `mise run solver:rebuild` ran first; for Rust-only LAHC changes the cpsat error is expected noise (LAHC cells are independent of the wheel). For a side-by-side smoke against master, do NOT prefix with `git stash --include-untracked` when the working tree is already clean (post-commit): `git stash` reports "No local changes to save" but does not error, so a follow-on `git stash pop` will pop a *prior* session's stash and may conflict with master's tip. Just `git checkout master`, run the bench, `git checkout <branch>` directly. Surfaced during the item-60 strict-`<` PR.
- **Pre-merge smoke does not surface the lahc_rr home_room collapse.** Production cell shape (60s × 20 seeds) on the 2026-05-06 refresh showed `worst_home_med` 0.50 → 0.05 on zweizuegig under `lahc_rr` / `lahc_rr_kempe` vs 1.00 under plain `lahc`. At the smoke shape (5s × 4 seeds × grundschule,zweizuegig), every LAHC variant reads `worst_home_med = 1.00` across both fixtures: the collapse only emerges as the LAHC budget grows past the FFD-greedy initialisation. Use the smoke for "did the new column render without panic" gates only; defer home_room directional reads (and any other axis the smoke shows uniformly across backends) to item 44's full refresh. Surfaced when item 22's `lahc_kempe` smoke at 5s × 4 seeds came back identical to `lahc` / `lahc_rr` / `lahc_rr_kempe` on the home_room axis even though the experimental hypothesis predicted divergence.
- **Picker tiebreak changes shift post-hoc quality predicates on real fixtures even when behavior-preserving on synthetic ones.** Strict-`<` cross-window selection passed every targeted test cleanly (`try_place_block_picker_*`), but the smoke bench at `--budget 5s --seeds 4 --fixtures grundschule,zweizuegig` showed `zweizuegig/lahc` worst_spread bumped 1 → 2 (still under the MAX_SPREAD=2 threshold) while soft score improved across every LAHC cell. Reason: the picker steers the FFD seed into a different region of the search space; LAHC's accept criterion converges on the canonical objective from there, but post-hoc spread / gap medians can move in either direction. Always run the smoke before assuming a picker tweak is "behavior-preserving"; synthetic tests cover the determinism contract, not the trajectory through real-fixture state. Item 60.

## solver-py rules

- **Thin wrappers only.** Every `solver-core` public symbol exposed to Python goes through a `#[pyfunction]` / `#[pyclass]` in `solver-py/src/lib.rs`. The wrapper marshals arguments, forwards, marshals the result back. No algorithm logic in `solver-py`.
- **Release the GIL on long calls.** Forgetting this serialises every caller behind the interpreter lock; the failure mode is invisible in single-threaded tests. PyO3 0.28 renamed `Python::allow_threads` to `Python::detach`; older snippets on the web still show `allow_threads` and no longer compile.

    ```rust
    #[pyfunction]
    #[pyo3(name = "solve_json")]
    fn py_solve_json(py: Python<'_>, problem: &str) -> PyResult<String> {
        py.detach(|| solver_core::solve_json(problem))
            .map_err(|e| PyValueError::new_err(e.to_string()))
    }
    ```

- **Disambiguate the Rust fn name from the Python-facing name** when the Python name already exists as a `solver-core` symbol. `scripts/check_unique_fns.py` in pre-commit rejects two `fn solve_json` definitions across the workspace; the PyO3 attribute `#[pyo3(name = "solve_json")]` on a differently-named Rust wrapper (`py_solve_json`) keeps the Python surface stable without colliding.
- **Errors map explicitly.** `solver_core::Error` to `PyValueError` for client mistakes (bad input shape), `PyRuntimeError` for solver-internal failures (timeout, internal invariant violation). Placement failures are not errors: they come back as `Violation` entries inside the `Solution`, so the wrapper returns them as normal data and the Python caller decides how to surface them. Use `From` impls or a small adapter for error paths; never `anyhow`.
- **Python tests exercise the binding contract, not the algorithm.** Tests at `solver/solver-py/tests/test_*.py` cover encoding, GIL release, error conversion. Narrow exception: a regression test for a bug that is binding-specific (e.g., float NaN handling across PyO3).
- **Maturin dev loop.**
    - Source-only edit in `solver-core` or `solver-py/src/lib.rs`: `mise run solver:rebuild` (wraps `uvx maturin develop --uv -m solver/solver-py/Cargo.toml`, seconds).
    - Edit touching `solver-py/pyproject.toml`, `Cargo.lock`, or the workspace `Cargo.toml`: `uv sync` (re-resolves the whole workspace, tens of seconds).
    - `mise run solver:rebuild` produces a **debug-profile** wheel by default (output: `Finished 'dev' profile [unoptimized + debuginfo]`), which means `cfg(debug_assertions)` is ON in `klassenzeit_solver` for the wheel that `mise run test:py` loads. The LAHC per-iteration `debug_assert_eq!(state.canonical_score, score_solution(...))` therefore fires in BACKEND pytest runs, not just `mise run test:rust`. Practical consequence: a backend integration test driving the solver via the HTTP route can surface an incremental-delta drift bug that no Rust unit / property test happens to cover; the symptom is `pyo3_runtime.PanicException: assertion left == right failed: LAHC must keep state.canonical_score == score_solution(...) at every iteration tail` propagating out of `solver_io.run_solve` as a 500 (or a raised exception under `httpx.ASGITransport(raise_app_exceptions=True)`). When investigating a backend-test panic of that shape, the fix lives in `solver-core/src/lahc.rs` (the canonical_score-maintaining call sites; search for `state.canonical_score`), not in the backend code path. Pattern surfaced 2026-05-11 in OPEN_THINGS item 11's flake-loop measurement on `test_seeded_grundschule_solves_without_pinned_teachers`, which routed through to filing item 76.
- **CP-SAT lives in `klassenzeit_solver.cpsat` as pure Python.** The "thin wrappers only" rule applies to PyO3 wrappers in `solver-py/src/lib.rs`. Peer Python algorithms in the `klassenzeit_solver` package are explicitly allowed; they do not call `solver-core` for the algorithm itself, only for utilities like `score_solution_json`. ADR 0030.
- **`score_solution_json` is the cross-backend scorer.** PyO3 binding in `solver-py/src/lib.rs` over `solver_core::json::score_solution_json` (which wraps `solver_core::score_solution` with `PRODUCTION_ACTIVE_WEIGHTS`). Used by `cpsat.py` to populate `Solution.soft_score` post-solve so all four bake-off backends compare on the same Rust scorer. ADR 0030.
- **`PRODUCTION_ACTIVE_WEIGHTS` is the canonical weight set.** Single `pub const` in `solver-core/src/types.rs`, re-exported from the crate root. The bake-off bench, `solve_json_with_config`, `score_solution_json`, and any future cross-backend scorer reference it; do not re-hand-write the weight literal.
- **CP-SAT module semantics:** Per-block-anchor binary encoding (`y[lesson, day, start_position, room]`). Pre-pruning at variable creation: subject suitability, teacher / room blocked time blocks, teacher qualification, window-fits-on-day. Hard constraints: cardinality, class/teacher/room non-overlap, teacher max-hours, same-room invariant via aux `z[class, subject, room]` booleans, lesson-group co-placement (pairwise sum equality), pinned placements (multi-block pins collapse to anchor at lower position). Objective mirrors `solver_core::score_solution` exactly (see the next bullet for the encoding). Determinism via `num_search_workers=1` and `random_seed=seed`. INFEASIBLE / UNKNOWN return one `NoFreeTimeBlock` violation per `(lesson, hour_index)` with `reason="cpsat: <status>"` per ADR 0027 wrapper-field pattern. MODEL_INVALID raises `RuntimeError`.
- **CP-SAT model objective mirrors `score_solution` exactly (item 48).** `_emit_objective` builds five summands: (1) per-anchor constant coefficient covering `prefer_early` + `avoid_first` + `avoid_last` + `prefer_late` (window-position arithmetic known at model build), (2) per-anchor constant coefficient for `prefer_home_room` (per-class mismatch boolean × N), (3-4) per-(entity, day, position) `present`/`has_left`/`has_right`/`gap` BoolVars with four channeling inequalities for `class_gap` and `teacher_gap` (`present` uses `add_max_equality` OR-semantics so multi-class lesson groups co-placed at the same `(class, day, pos)` resolve to a 0-1 indicator matching `score_solution`'s per-(class, day) `dedup()`), (5) per-class `c_count`/`dev`/`scaled`/`quotient` chain via `add_abs_equality` + `add_division_equality` for `class_day_balance`. Every weight in the objective mirrors `solver_core::types::PRODUCTION_ACTIVE_WEIGHTS`; module-level constants `_W_*` in `cpsat.py` keep them legible. The contract `solver.objective_value == score_solution_json(problem, placements)` is pinned by `test_cpsat_objective_value_equals_score_solution_on_<fixture>` in `solver/solver-py/tests/test_cpsat.py`. When a new soft-cost axis lands in `score_solution` (new `ConstraintWeights` field plus a new term in the weighted sum), extend `_emit_objective` in lockstep or the property test goes red. Each `_objective_*` axis helper returns `cp_model.LinearExpr | int` so the no-terms early-out can return the literal `0`; `cp_model.LinearExpr.sum([])` does not flatten cleanly into `model.minimize(... + summand)` and `ty` flags a bare `cp_model.LinearExpr` annotation when one branch returns `int`.
- **Adding a soft-cost axis to CP-SAT touches three sites in `cpsat.py` plus the `_emit_objective` summand list.** When a new `ConstraintWeights` field lands and `score_solution` grows a matching weighted term, the CP-SAT mirror requires (1) a module-level `_W_<AXIS>` constant matching `PRODUCTION_ACTIVE_WEIGHTS.<axis>`, (2) a new `_objective_<axis>_term(...)` helper returning `cp_model.LinearExpr | int` with the same closed-form the scorer computes (e.g. `prefer_class_teacher`'s helper sums `_W_PREFER_CLASS_TEACHER * mismatch_indicator` per (class, subject) pair where the class has a qualified `class_teacher_id`), and (3) a new summand line inside `_emit_objective` adding `_objective_<axis>_term(...)` to the running expression. Missing any of the three breaks the `solver.objective_value == score_solution_json(...)` parity test silently in directions that are easy to misread (e.g. CP-SAT objective value low because the new penalty isn't summed in, but the post-extracted placements still incur the penalty in `score_solution_json`'s recompute, so the bench's per-component column reads non-zero while the CP-SAT internal objective declares 0). Pattern surfaced 2026-05-09 in item 67's `prefer_class_teacher` mirror.
- **OR-Tools API: use snake_case method names.** `cp_model.CpModel.add`, `new_bool_var`, `minimize`, `solve`, `value`, `status_name`, NOT the deprecated camelCase aliases (`Add`, `NewBoolVar`, etc.). The camelCase forms still exist at runtime for backwards-compat but `ty` does not see them as attributes and flags every call as `unresolved-attribute`. Pattern surfaced in Sprint 4's `cpsat.py`.
- **CP-SAT class non-overlap dedupes by `(class_id, lesson_group_id)`.** Multi-class lesson groups (per-Jahrgang Religion trio: 3 lessons spanning the same 3 classes via `school_class_ids`, sharing one `lesson_group_id`) co-place at one `(day, pos)`. If `_emit_non_overlap` adds one var per (lesson, class) without dedup, each shared class accumulates `sum=3` against `sum<=1` while the lesson-group co-placement constraint forces all three members equal, so the model is INFEASIBLE by construction. Pattern: `class_group_first[(c_id, group_key)] = (l_id, [vars])` keeps only the lowest-`l_id` member's per-room vars; teacher and room non-overlap do NOT dedup today (existing fixtures have distinct teachers/rooms across group members; extend if Doppelbesetzung / Foerderstunden lands). Surfaced by the Sprint 4 follow-up dreizuegige investigation; regression test `test_solve_cpsat_json_multi_class_lesson_group_co_places_at_same_slot` in `solver/solver-py/tests/test_cpsat.py`.
- **CP-SAT INFEASIBLE is distinguishable from UNKNOWN by wall-clock.** When the bake-off bench reports `0/N` on a fixture, run `solve_cpsat_json` from Python directly (longer budget, capture violation `reason`): `cpsat: infeasible` returns in ~1.4s on dreizuegige (model over-constrained), `cpsat: unknown` would burn the full deadline (search timeout). The bench harness throws away the reason; bench wall-clock much smaller than budget on a `0/N` cell is the smell that something is structurally wrong, not budget-bound. Surfaced when the OPEN_THINGS bullet's "timed out" hypothesis turned out to be a model bug.
- **Bench-fixture debug probe.** To investigate a CP-SAT or LAHC outcome on a `solver_core::test_fixtures` fixture without modifying the bench harness, scratch-build at `/tmp/probe-bin/`: tiny `Cargo.toml` with `solver-core = { path = ".../solver/solver-core" }` and `serde_json`, 5-line `main.rs` that calls the fixture builder and `println!("{}", serde_json::to_string(&p).unwrap())`. Pipe to a JSON file; then `uv run python3 -c "from klassenzeit_solver.cpsat import solve_cpsat_json; ..."` against it for direct debugging at any budget / seed.

## Clippy and allows policy

- No `#![allow(...)]` at crate root, ever.
- No `#[allow(...)]` at item scope unless one of:
    1. A specific lint the contributor judges wrong in this block, with a sibling `// Reason: ...` comment naming why.
    2. PyO3 macro expansion noise (e.g., `clippy::needless_pass_by_value` from `&Bound<'_, PyModule>` in `#[pymodule]` signatures). Allow locally on the wrapper.
- No `#[allow(dead_code)]` outside `#[cfg(test)]`. If you think you need it, run `cargo machete` (already in `mise run lint:rust`); it often surfaces the dependency you actually want to remove.
- **`clippy::type_complexity` on `const` declarations resolves via a type alias, not `#[allow]`.** Hot pattern: `const FIXTURES: &[(&str, fn() -> Problem)]` trips the lint; replace with `type FixtureEntry = (&'static str, fn() -> Problem); const FIXTURES: &[FixtureEntry] = &[...];`. The alias is `'static` either way (string literals plus fn pointers) and it documents the intent better than the inline tuple shape. Surfaced when adding `solver-bench`.

## Commit scopes

Use the crate directory as Conventional Commits scope:

- Good: `feat(solver-core): greedy first-fit placement`.
- Bad: `feat(solver): greedy first-fit placement` (loses the which-crate signal when `solver-py` also gets a commit that week).

Bare `solver` scope only when a paired change genuinely spans both crates (e.g., new public API in `solver-core` plus its binding in `solver-py` in one atomic commit). `.github/commit-types.yml` enforces commit *types*; scopes are free-form but a consistent convention keeps `git log` grep-friendly.

## Bench workflow

- **`mise run bench`** runs the criterion bench (`cargo bench -p solver-core --bench solver_fixtures`). Use for the "am I faster than yesterday?" inner loop; the second run's criterion output shows deltas against the first.
- **Criterion bench cfg uses `PRODUCTION_ACTIVE_WEIGHTS` (item 15).** `bench_greedy_cfg` and `bench_lahc_cfg` in `solver-core/benches/solver_fixtures.rs` both build `SolveConfig { weights: PRODUCTION_ACTIVE_WEIGHTS, .. }` since the 2026-05-07 fix. Earlier the bench used a narrower `class_gap=1, teacher_gap=1` set; once the same-room hard constraint landed in solver-core, `solver_greedy/zweizuegig` started panicking on `assert!(solution.violations.is_empty())` because FFD couldn't escape an FFD lock-in (lesson 66 = 4b SP, `NoSuitableRoom` at hour 2: only two Sport rooms for 8 classes × 3 SP-hours under same-room locking) without the home_room and class_day_balance pull production weights provide. The bench's perf measurement is still meaningful; it now exercises the same code paths production exercises. Greedy timings are 5-8x higher than the pre-fix BASELINE because production weights compute more cost axes per `try_place_block` call; LAHC stays deadline-bound at 200 ms. Don't switch the bench back to a narrower weight set without re-validating feasibility on every fixture.
- **The 20% criterion regression budget guards hot-loop changes, not one-shot completion costs.** A single `score_solution(...)` call at the end of `solve_with_config` measured +37% on `solver_greedy/grundschule` (45 placements, ~99µs total) when the addition is ~27µs absolute; the same call is <0.02% of the production LAHC 5 s deadline. Triage criterion deltas by absolute µs on tiny fixtures, not by percentage; refresh `BASELINE.md` and surface in PR body. Pattern surfaced when item 41 added `solution.soft_score = score_solution(...)` at solve completion.
- **`mise run bench:record`** re-runs the bench and overwrites `solver/solver-core/benches/BASELINE.md`. Run this if and only if the PR intentionally changes solver performance. The 20% regression budget (see the two bullets above) applies against the committed `BASELINE.md`, not a personal baseline.
- **The bench does not run in CI** (shared runners are too noisy for a 20% budget). Algorithm-phase PRs cite the `BASELINE.md` diff in the PR body.
- **Host sensitivity.** The committed numbers anchor to the recording host; when a maintainer refreshes them they should do so on comparable hardware. The footer in `BASELINE.md` records CPU, kernel, and rustc version so reviewers can judge whether a drift is plausible.
- **Fixtures:** three sizes inside one criterion group: `grundschule` (2 classes, 15 lessons, 45 placements), `zweizuegig` (8 classes, 68 lessons, 196 placements), and `dreizuegig` (12 classes, 102 lessons, 294 placements; exercises lesson-group co-placement via the per-Jahrgang Religion trios). Builders live in `solver-core/src/test_fixtures.rs` (default-on `fixtures` feature; solver-py opts out) and are imported by both the criterion bench and the bake-off bench, so drift between the two is structurally impossible. A fourth size (`gesamtschule`) is tracked under `OPEN_THINGS.md` "Acknowledged deferrals".
- **FFD is invariant to lesson input order.** Both bench fixtures iterate subjects in the natural authoring order; `ordering::ffd_order` inside `solve_with_config` sorts lessons by eligibility before placement so the global solve succeeds regardless of input permutation.
- **`mise run bench:bakeoff`** runs the bake-off bench (`cargo run -p solver-bench --release`) per `(fixture, backend, seed)` cell against the production active-default `ConstraintWeights` and rewrites `solver/solver-core/benches/BENCH_RESULTS.md`. Output is host-stable on feasibility / hard-violations columns and host-sensitive on wall-clock columns. Default cell shape is 60s × 20 seeds × 4 fixtures × 1 backend (~80 min wall-clock); downscale during dev with `mise run bench:bakeoff -- --budget 5s --seeds 4 --fixtures grundschule --out /tmp/...`. Methodology: ADR 0029.
- **Two artifacts, two purposes.** `BASELINE.md` (host-sensitive, criterion, 20% regression budget) gates perf regressions on algorithm PRs. `BENCH_RESULTS.md` (host-stable on feasibility, bake-off bench) gates feasibility regressions when a backend changes or a fixture is added. Neither runs in CI; algorithm-phase PRs cite the relevant diff in the PR body.
- **Production-default ADRs reason from per-component vectors.** ADR 0031, 0032, and any future production-default ADR (e.g., the next available number for OPEN_THINGS item 47, at minimum 0037 since ADR 0036 is now the solver-driven teacher-assignment ADR landed in item 61; always `ls docs/adr/*.md | sort | tail -1` before assigning) must compare backends against the per-component columns in BENCH_RESULTS.md (`class_gap_h`, `teacher_gap_h`, `home_room_miss`, `day_balance`, plus the four schedule-quality predicates), not just the `Soft score` collapsed scalar. The "Backend objectives" section above the table makes drift between an internal objective and the canonical scorer legible; an ADR that picks a backend whose internal objective declared-skips half the axes solely because its post-hoc soft score is lower is reading the wrong column. Item 51.
- **New backends register in `solver_core::quality::build_backend_objectives`.** The bench renderer calls `solver_core::backend_objective(name)` for each known backend and panics on `None` (`solver-bench/src/main.rs:855`'s `unwrap_or_else(|| panic!(...))`). A new Rust backend (or a Timefold spike per item 55) must add a `BackendObjective` row declaring its `optimised` and `declared_skipped` `QualityComponent` sets, otherwise the bench cannot render it. Two-commit shape when splitting across crates per the Conventional Commits scope rule: (1) `feat(solver-core): register <name> BackendObjective` (quality.rs row + the two `backend_objective_*` test slices grow to include the new name; the test slice is the RED gate), (2) `feat(solver-bench): wire <name> BenchBackend variant` (enum + `label` + `parse` + `ALL` + dispatch + end_to_end row assertion). Registration MUST land before wiring; cherry-picking commit 2 alone to a branch lacking commit 1 panics on every bench run. Squash-merge collapses both onto master atomically. Pattern from item 22's `lahc_kempe` addition. The declaration describes today's reality, not the desired end state; as items 48 / 52 / 54 land, components move from `declared_skipped` into `optimised` in their own commits.
- **Bench markdown-row substring assertions anchor on cell delimiters, not bare labels.** `body.contains("| lahc_kempe |")`, not `body.contains("lahc_kempe")`: the bare form matches `lahc_rr_kempe`'s suffix and passes spuriously even before the new variant exists. The Backend objectives table renders rows as `| {label} | ... |` with single-space padding (`solver-bench/src/main.rs:867`), so `| {label} |` is unambiguous. Same shape for any future bench-row substring assertion in `solver/solver-bench/tests/end_to_end.rs` or in the inline rendering tests. Surfaced during item 22 plan-time review; the bare-substring form would have made the end_to_end RED gate unreachable.
- **Inserting an H2 into the bake-off markdown splits the table.** `solver-bench/src/main.rs` separates `write_title_and_intro` (everything above the data) from `write_table_header` (the column row plus separator). Anything that needs to land between the intro and the data table must be inserted between those two calls; placing a `## …` heading after `write_table_header` terminates the table at the heading and orphans the data rows underneath. Surfaced when item 51 added the "Backend objectives" section.
- **`mise run bench:bakeoff` adds a `cpsat` column** in addition to `lahc` / `lahc_rr` / `lahc_rr_kempe`. The cpsat backend invokes `python3 -m klassenzeit_solver.cpsat` per cell as a subprocess. The mise task wraps `cargo run` in `uv run` so the cargo-spawned `python3` resolves to the workspace venv automatically; no operator-side activation needed. Full refresh wall-clock at production settings (`--budget 60s --seeds 20`) is approximately 5 hours on a quiet AMD Ryzen 7 3700X (8C/16T) post-items-30+31; the original ADR 0029 estimate of 4.5 h predates the per-seed quality recompute and the ttf / tto / peak-RSS columns. Dev-loop downscale via `--budget 5s --seeds 4 --fixtures grundschule`. Production default per [ADR 0031](../docs/adr/0031-solver-production-default.md), reaffirmed against the post-item-37 corrected bench data in [ADR 0032](../docs/adr/0032-solver-production-default-revisit.md).
- **Run `mise run solver:rebuild` before any production-budget `bench:bakeoff`.** The CP-SAT cells subprocess into `python3 -m klassenzeit_solver.cpsat`, and `klassenzeit_solver` is a maturin-built editable wheel; a wheel that lags behind solver-core / solver-py drifts the CP-SAT cells silently (off feasibility, off soft-score) without any error surfacing. Pure Rust LAHC backends compile fresh from source via `cargo run --release` and are unaffected. The rebuild step is cheap (~5 s) compared to the 5 h cost of a wasted production run; treat it as mandatory pre-flight, not optional.
- **`cargo nextest` does not propagate the `uv` venv to subprocess `python3`.** A solver-bench end-to-end test that spawns the supervisor binary (which in turn spawns `python3 -m klassenzeit_solver.cpsat` per cpsat seed) sees `ModuleNotFoundError: No module named 'klassenzeit_solver'` on the cpsat path because nextest's spawned binary inherits a stripped env. Production `mise run bench:bakeoff` wraps `cargo run` in `uv run`, so the venv resolves there. Tests that absolutely need the python child must `uv run cargo nextest ...` or set `PYTHONPATH` explicitly; otherwise design the smoke to assert only the markdown shape (cpsat failure on the smoke is acceptable; production refresh covers it).
- **`solver-bench` is supervisor + cell-child via recursive self-spawn.** Default mode parses CLI, then spawns one `solver-bench --cell <fixture> --backend <name> --budget <d> --seeds <n>` child per `(fixture, backend)` pair. The cell-child runs the seed loop in-process for LAHC, spawns python per seed for cpsat, reads its own peak RSS via `libc::getrusage(libc::RUSAGE_SELF)` at exit, and emits a single `CellResult` JSON object on stdout. Each cell's peak RSS is honest because each cell runs in its own process; a single-process bench would report monotonic-cumulative `ru_maxrss` instead. ADR 0034. The bench therefore has one runtime dep deviation from the "no external runtime deps" rule above: `libc = "0.2"` for the syscall binding. Documented in ADR 0034.
- **Schedule-quality predicates live in `solver-bench/src/quality.rs` as `QualityPredicates` (renamed from `QualityReport` in item 50; the new core-side `QualityReport` is the cost-vector breakdown).** Pure functions over `&Problem` + `&Solution`; mirror by intent the predicates `backend/src/klassenzeit_backend/scheduling/quality_checks.py` enforces in `test_grundschule_schedule_meets_quality_bar`. Cross-language parity is intentionally not a contract: the Python evaluator operates on persisted ORM rows with a hand-supplied exempt-subjects set; the Rust evaluator operates on the in-memory `Solution` and infers exempt subjects from `Problem.room_subject_suitabilities` (a subject is exempt for a class iff the subject has any suitability rows AND the class's `home_room_id` is not in that subject's suitable rooms). Bench `CellResult` carries five `QualityPredicates` median fields (`worst_spread_median`, `worst_home_room_ratio_median`, `total_interior_gaps_median`, `late_period_ratio_median`, `quality_pass_count_median`); BENCH_RESULTS.md renders a `Quality (pass / 4)` column. Late-period predicate uses `Subject.prefer_late_period > 0` as the proxy for "FÖ-shaped"; the proxy is set on the FÖ subject in the zweizügig (i==8) and dreizügig (i==10) fixtures since item 12 shipped (2026-05-07). On a fixture where no subject carries `prefer_late_period > 0` (e.g. grundschule today), the cell renders `-` and counts as pass for the composite Quality column. Thresholds in `quality.rs::QUALITY_*` constants match the Python test verbatim (`MAX_SPREAD = 2`, `MIN_HOME_ROOM_RATIO = 0.6`, `MAX_INTERIOR_GAPS = 2`, `MIN_LATE_PERIOD_RATIO = 0.5`).
- **Bench `Quality (pass / 4)` data does NOT predict integration-test pass on the solver-driven teacher path.** The bench fixture pins teachers via `_TEACHER_ASSIGNMENTS_*` (documented in `backend/CLAUDE.md` under "**`_TEACHER_ASSIGNMENTS_<NAME>` dicts pin teacher allocation in seed solvability tests.**"); integration tests on the solver-driven teacher path (`test_grundschule_schedule_meets_quality_bar`, `test_seeded_grundschule[_zweizuegig|_dreizuegig]?_solves_without_pinned_teachers`) go through `POST /api/classes/{id}/generate-lessons`, which since item 63 leaves `Lesson.teacher_id` null and lets the solver pick among `teacher_candidates` per ADR 0036. The integration tests thus solve a strictly larger search space than the bench cell (per-Lesson teacher decision instead of a pre-pinned teacher). Before item 74 closed 2026-05-11, the FFD picker could double-book teachers under widened candidates (`try_place_group` collapsed every member's teacher to `teacher_candidates[0]`; post-solve readers consumed `lesson.assigned_teacher_id()` which fell back to the same static index); the fix routes group-window teacher selection through `chosen_teachers: HashSet<TeacherId>` and switches `validate_no_double_booking` / `score_solution` / `quality_report` to `Placement.teacher_id`. Surfaced 2026-05-08 against item 14 (bench grundschule `quality 4/4` on every backend at 60 s budget, integration test 20/20 RED on `body["violations"] == []` at the production 5000 ms budget); item 73's 2026-05-11 unpinned-variant bench refresh isolated the picker gap (every LAHC unpinned cell panicked on `double-booking`), confirming the pinned-vs-unpinned cost-of-widening is structural, not noise. When citing bench quality data as evidence for a planned integration-test xfail removal, the right gate is "20-of-20 PASS on the integration test at the test's wall-clock budget on the unpinned bench shape", not "bench quality 4/4" on the pinned shape. The gap surface keeps migrating as fixes land: the 2026-05-12 item-14 flake-loop produced 3/20 RED on `check_class_day_balance` `spread=3-4 > max_spread=2` (item 57's surface, closed in lockstep with item 14 reaching 20/20 PASSED post-widening); the 2026-05-12 item-11 round-2 flake-loop went 20/20 PASSED on einzügig at production `solve_deadline_ms=5000` but 7/20 RED on zweizuegig + 12/20 RED on dreizuegig with `teacher_over_capacity` dominant, now tracked under item 79 (solver teacher-picker over-allocation on multi-school unpinned mode). Rule shape unchanged across migrations; future xfail-removal items on these tests gate on the same 20-iteration flake-loop and route the remaining RED shape to the matching open item.
- **Adding a new bench tunable column is a four-site plumb plus a cell-child JSON gate.** When `solver-bench` gains a new optional cell-spec field the supervisor cross-products into `(fixture, backend)` cells (item 21's `--rr-k` / `--rr-period`, item 23's `--kempe-max-chain`), the column rendering touches FOUR sites in `solver-bench/src/main.rs`: `write_table_header` (column header + separator), `write_row` (data cell), `write_error_row` (the matching `| - |` cell so an error row's column count matches a data row's), and `render_cells_with_specs` (the orchestrator that wires the per-cell flag through). A miss in any one produces a column-count drift the markdown table renders silently; the regression test `supervisor_emits_observability_and_quality_columns` (kept on the no-flag path so it stays column-set-stable) plus the new flag's own end-to-end test guard the parity. Pattern: add a `render_<col>_col: bool` parameter computed once at the top of the rendering pipeline as `cells.iter().any(|c| c.<field>.is_some())`, then plumb through every row writer. The cell-child JSON echo at the `CellResult` literal MUST gate on the dispatch path actually using the field (compare `rr_k: if dispatch_rr_period.is_some() { Some(lahc_rr_k) } else { None }`); an unconditional echo creates inconsistent JSON for any future cell-child caller bypassing the supervisor's cross-product guard. Cell-child fn signatures often hit `clippy::too_many_arguments` at 8 params after a new override lands; resolve via an overrides struct (`LahcCellOverrides` precedent) rather than `#[allow(clippy::too_many_arguments)]` per the no-allow policy. Item 23 surfaced the four-site plumb count and the JSON-echo asymmetry footgun.
- **Production-budget `bench:bakeoff` is supervised via `run_in_background` + a persistent `Monitor`, not foreground sleep loops.** A 5-6 h foreground bash blocks the orchestrator session, and Claude Code rejects `sleep 90`-style chains as a workaround (the runtime emits a "use Monitor with an until-loop" error). Clean pattern: `Bash run_in_background: true` against `mise run bench:bakeoff -- ... > /tmp/kz-bench-<topic>.log 2>&1`, then arm a `Monitor persistent: true` with `tail -F <log> | grep -E --line-buffered "cell done|panic|thread .* panicked|FATAL|Killed|Error|fatal runtime"`. The supervisor's per-cell `cell done:` log line emits one notification per finished cell (production cell shape = 20 cells = 20 progress events at ~18 min spacing). `panic` and `Error` patterns surface failures within seconds. The supervisor's exit fires the `run_in_background` completion notification on its own. `ScheduleWakeup` is /loop-mode only and does not apply here; `Monitor` covers the streaming case directly. Pattern surfaced supervising the item 44 production refresh on 2026-05-08; re-validated 2026-05-11 under item 73 across the two-invocation pinned/unpinned shape (see the two-invocation refresh rule below), including the unpinned variant's per-cell `panic` notifications surfacing item 74's picker bug within seconds of the first cell exiting.
- **Pre-flight host-quiescence check before a production-budget sweep.** `uptime` plus `ps -eo pcpu,pmem,etime,comm --sort=-pcpu | head -10` before kicking off. The bench is host-sensitive on wall-clock and Peak RSS columns; sibling processes pinning a core (a stuck `awk` from a prior `fewer-permission-prompts` run, a wedged cron-driven Claude session, an Obsidian indexer in a tight loop) double the wall-clock medians and contaminate cross-refresh comparisons. If a process has been at 99.9% CPU for hours / days and its command line is a clearly-stuck filter, killing it is safe; surface the kill to the user before the 6 h commitment. Feasibility / hard-violation columns stay host-stable so a noisy host doesn't invalidate the data, only the wall-clock columns. Item 44's pre-flight on 2026-05-08 caught four 2-day-old stuck `awk` processes pinning four of eight physical cores.
- **`bench:bakeoff` writes BENCH_RESULTS.md atomically at end-of-run.** The supervisor accumulates per-cell results in memory and emits the markdown after the last cell (final log line `wrote "solver/solver-core/benches/BENCH_RESULTS.md"`). During the multi-hour run, the on-disk file remains the prior version; do not poll it for partial progress. Per-cell observability lives in the supervisor's stdout / stderr (`cell start:` / `cell done:` lines and any `panic` traces). The atomic end-of-run write also drops sections inserted by earlier `--append` runs (e.g. the `## RR sweep <date>` section item 21's tuning produced); default mode rewrites the whole artifact. Acceptable for full refreshes that supersede prior sweeps; if a sweep section deserves to live across a refresh, save it elsewhere (its own ADR, a `docs/research/<date>-<topic>/` dir) before running the refresh.
- **`solver_core::quality_report` is the backend-neutral cost-vector breakdown.** `quality_report(problem, placements, violations, weights) -> QualityReport` walks the same partitions `score::score_solution` walks and returns one raw-count field per cost axis (`hard_violations`, `unplaced_hours`, `class_gap_hours`, `teacher_gap_hours`, `class_day_balance_cost`, `home_room_misses`, `prefer_early_units`, `avoid_first_units`, `avoid_last_units`, `prefer_late_units`) plus `weighted_score`. The contract `quality_report.weighted_score == score_solution(problem, placements, weights)` is pinned by `solver-core/tests/quality_property.rs::quality_report_weighted_score_matches_score_solution` under random weights; adding a new soft-cost axis to `score_solution` (new `ConstraintWeights` field plus a new term in the weighted sum) requires extending `QualityReport` with a raw-count field and the same term in `weighted_score`'s aggregation, or the property test goes red. `score_solution` stays in the LAHC hot path (single u32 return, no allocation); `quality_report` is cold-path only (post-solve, bench, ADR comparison). Bench `CellResult` carries nine `QualityReport` median fields (the two already-present `hard_violations_median` and `soft_score_median` cover `hard_violations` and `weighted_score`); markdown renders four load-bearing columns (`class_gap_h`, `teacher_gap_h`, `home_room_miss`, `day_balance`). New columns added to `write_header` / `write_row` need lockstep updates in `solver-bench/tests/end_to_end.rs::supervisor_emits_observability_and_quality_columns` and the inline `write_row_renders_quality_columns` test (both assert on column-header presence in the rendered markdown). Item 50 ships the contract; items 51 / 52 / 48 enforce backend objective parity against the same vector.
- **Bench-side enum method names already include `parse` and `label` via `BenchBackend`.** `solver-bench/src/main.rs` declares `BenchBackend::parse(&str) -> Result<Self, String>` and `BenchBackend::label(self) -> &'static str` as the canonical pattern for CLI-parsed enums in the bench. When adding a sibling enum (e.g. `TeacherPinsMode` for item 73), reusing `fn parse` / `fn label` on the new type trips `scripts/check_unique_fns.py` because methods on different types still share a fn-name namespace in this repo. Per the project's unique-function-names rule the resolution is to rename the NEW methods (e.g. `parse_teacher_pins_mode`, `teacher_pins_label`), not `BenchBackend`'s. Surfaced 2026-05-11 in item 73's `feat(solver-bench): add --teacher-pins toggle`.
- **`--teacher-pins=on|off` toggles bench-side teacher pinning.** Default `on` matches the canonical fixture shape (every `Lesson` is `teacher_pin: Some(t)`, `teacher_candidates: [t]`); the all-pinned table at the top of `BENCH_RESULTS.md` is the comparable artifact across refreshes. `off` calls `unpin_teachers_in_problem(&mut Problem)` post-fixture-build to clear `teacher_pin` and widen `teacher_candidates` to the deterministic-sorted, deduplicated set of qualified teachers per subject (from `Problem.teacher_qualifications`). Use `off` to exercise the solver-driven teacher-assignment path (ADR 0036); the unpinned data captures the cost of widening teacher decision variables relative to the constrained shape. The transform is local to `solver-bench/src/main.rs`; the in-tree `solver-core` fixture builders are not parametrised so the criterion bench and integration tests stay on the canonical pinned shape. Surfaced 2026-05-10 in item 73.
- **Two-invocation production refresh for the (un)pinned cross-section.** A full refresh that captures both data sets is two sequential supervisor invocations against the same `--out` path; the second is `--append`-mode and emits a `## Unpinned variant (solver-driven teacher assignment, ADR 0036)` H2 plus preamble before its table. Operator shape: `mise run solver:rebuild`; then `Bash run_in_background: true` with `mise run bench:bakeoff -- --teacher-pins on > /tmp/kz-bench-<topic>-pinned.log 2>&1` plus a persistent `Monitor` tailing the log; wait for completion (5-6 h); then a second `run_in_background` with `mise run bench:bakeoff -- --teacher-pins off --append > /tmp/kz-bench-<topic>-unpinned.log 2>&1` (NOT in parallel; the bench is host-sensitive on wall-clock and Peak RSS). Item 73 supervised this pattern on 2026-05-10. Note: under `--teacher-pins=off`, the FFD greedy can panic on tightly-constrained fixtures because the picker has no cross-lesson teacher coordination beyond the per-(class, subject) lock; the bench supervisor handles panicked cells gracefully via `write_error_row` (renders `panic` in the Feasibility column) and continues to the next cell, so the unpinned section can carry panic rows that are themselves informative data.
